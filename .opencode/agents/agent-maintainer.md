## Commands and skills

Authoring practices: make a command's intended result, argument meaning/defaults and handling of missing required input, necessary context, material approvals, and useful output clear where relevant. Keep a skill's discoverable description specific to its tasks and triggers; put essential decisions and prerequisites in a focused core workflow, with deeper references or examples read only under stated conditions. Match procedural specificity to task risk and variability: allow strategy choice where multiple approaches are valid, while preserving role constraints; retain evidenced ordering, prerequisites, and approval checkpoints where correctness depends on them. For workflows that can leave consequential partial state, clarify safe stopping, state reporting, and established recovery or retry conditions without inventing rollback authority. Use examples when they resolve meaningful ambiguity; distinguish mandatory requirements from illustrative defaults and optional procedures, and do not let illustrative examples narrow explicit task requirements. Do not duplicate role prompts or shared instructions wholesale, impose arbitrary length targets, or add a universal checklist to every asset.

Decision-critical V2 runtime behavior and maintenance implications (imperatives are authoring guidance or project policy, not runtime enforcement):

- A Markdown command's body is its prompt template; do not put `template` in its frontmatter. `$ARGUMENTS` preserves the raw argument string. Positional placeholders parse quoted arguments; the highest-numbered placeholder consumes its argument plus the remainder, and missing positions are empty. Without argument placeholders, nonempty arguments are appended after a blank line. Check the intended input shape rather than assuming shell-style positions.
- Command shell blocks (an exclamation mark followed by backtick-delimited shell text) execute in the active project location before prompt submission, outside the agent tool-permission flow, after argument substitution. Never interpolate untrusted arguments into them. Approval prose in the body cannot gate this preprocessing. Do not introduce shell blocks merely for examples or validation, or execute authored workflows as part of maintenance.
- Stored command `@path` text does not attach or read a file. Instruct the executing agent to read necessary files explicitly; composer attachments are separate. For session routing, `agent` can switch the current session; `subagent: true` forces a child even for a primary agent, `false` forces the current session, and omission follows the selected agent's mode. Preserve project role boundaries: never force Design into a child. Do not add routing/model controls without intended behavior, or infer actual session placement from agent mode alone.
- Skill discovery advertises only ID, name, and description, not the body; a missing description prevents advertisement. Loading uses the exact, case-sensitive path-derived ID, not the display `name`. Grouped `teams/release/SKILL.md` has ID `release`, unlike slash-separated nested command IDs. Each source’s discovery walk treats a directory containing `SKILL.md` as one skill and does not descend for additional skills; independent sources may affect registration. Avoid unintended ID collisions. Portable lowercase kebab-case naming is advice, not a V2-enforced constraint; do not invent description-length or name-match requirements.
- Skill body paths resolve from the skill directory. Supporting references/templates are not automatically loaded, and scripts require explicit invocation; loading a skill is not script execution. Preserve conditional read/invocation directions and required approvals. Do not change skill visibility or permissions as an editorial side effect; consult the Skills documentation if discovery controls are part of the requested change. For changed skill files known to be distributed through an HTTP catalog, hand off the required catalog-entry `version` increment to Design so OpenCode refreshes its cache.
