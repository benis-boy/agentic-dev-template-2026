Improve the project's Markdown documentation so it is trustworthy, navigable, and appropriate to its audience. `$ARGUMENTS`, when supplied, gives optional focus areas or priorities; use it to order work, not silently shrink the default full-repository inventory. Do not use shell interpolation for it.

This is a bounded review-and-repair workflow, not a mandate to restructure docs, create a documentation program, or make every file stylistically uniform. Preserve unrelated staged, unstaged, and untracked work. Make small evidence-supported editorial, retirement, and link fixes. For tracked, unchanged docs, evidence-supported retirement under the policy below is normal cleanup work and needs no separate approval solely because it deletes a file; ask the human before material changes to retained requirements or meaning, authority changes, or resolving ambiguous conflicts.

## Inventory and map

1. Start at the project root. Read applicable root and nested `AGENTS.md` guidance and your own current prompt. Read linked operational guidance when it applies; links do not load themselves. Never assume a child agent knows a parent or sibling prompt.
2. Inventory first-party Markdown recursively, including hidden directories, root and nested `AGENTS.md`, case-insensitive `.md`, and other Markdown extensions actually used (for example `.markdown`, `.mdx`, `.mdown`, or `.mkd`). Include root and package READMEs, monorepo/package documentation, docs-site content, MDX, and untracked first-party docs. Preserve untracked docs under the user-work safeguard below. Do not follow symlinks outside the project.
3. Classify the inventory using the repository's own structure, not a prescribed folder layout. For each family, identify its purpose, audience, package/product area, lifecycle or version applicability, likely owner, canonical source for key facts, and useful adjacent docs. A concise inventory map by family/package is enough; do not create a persistent tracking system or report artifact unless requested.
4. Adapt this taxonomy to what exists: entry-point READMEs and onboarding/contributing; tutorials, how-to/task guides, and exhaustive API/CLI/schema/config reference; architecture, design, security, ADRs, RFCs, specifications, plans, and proposals; operations, runbooks, deployment, recovery, and troubleshooting; changelogs, releases, migrations, deprecations, versioned or archived material; legal/compliance and localized docs; generated reference and docs-site/MDX content. It is a classification aid, not a request to add every document type or create new directories.
5. Exclude dependency/vendor, VCS, build, cache, and generated/artifact areas only when justified by project guidance or evidence, and name those exclusions. Do not blindly ignore generated docs or their links: identify generated outputs and their authoritative source, review references/routing as appropriate, and state what could not be inspected or regenerated. Treat unreadable files and scope exclusions separately from reviewed files.
6. For a large inventory, prioritize shared/canonical documentation and high-dependency navigation first, then work in bounded batches grouped by family/package and adjacent docs. Keep mutually exclusive coverage totals: reviewed unchanged, edited (including partially retired), deleted, deferred/skipped with reason, and unreadable/unreviewed. Identify uncovered groups compactly; give exact path lists only when useful and manageable, otherwise offer a bounded continuation. Focused arguments can defer lower-priority batches but never justify claiming full-repository cleanup.

## Review by document type

Across documents, assess factual support, clarity, audience fit, ownership, duplication, headings/frontmatter/fences, document references, and navigation. Check inbound as well as outbound links before any approved move or rename. Use existing navigation, indexes, routes, redirects, includes, and canonical-source conventions. Add meaningful cross-links where they help readers move between related material; avoid all-to-all links and bare link substitutions without understanding their context.

Actively review document references for both validity and continued usefulness:

- Inventory actual local document paths/anchors and external URLs in the reviewed documents, including plain-text and backtick paths when they serve as real document references, not just Markdown links. Distinguish placeholder tokens, illustrative examples, generated routing conventions, and intentionally historical links from current filesystem targets; do not label these broken merely because no literal local file exists.
- Check local target existence and anchors using the applicable path base and docs-site routing conventions. Arrange bounded, read-only direct checks of inventoried external URLs through the validation ownership below; deduplicate checks where useful. Assess redirects, destination content, supported version applicability, and relevance to the surrounding claim or task. A reachable but irrelevant or obsolete page is not a good reference. Do not recursively crawl linked pages, install tools, authenticate, or run side-effecting workflows. Record timeout, network, authentication, rate-limit, and other inconclusive responses as unverified, not automatically dead; report checks that cannot be performed.
- Repair references only with evidence of the intended authoritative target. Remove a no-longer-useful reference only when bounded editorial repair preserves retained meaning and requirements; otherwise escalate uncertainty or material changes under the approval policy. Preserve useful historical context and do not guess replacement paths or URLs from names alone.

Distinguish what is proposed or intended from what is implemented today and what has been verified. Compare claims with authoritative source/docs or evidence, but do not make documentation agree with broken, insecure, or surprising code merely because it exists. Do not silently promote plans into current behavior or mark them stale based only on age. Preserve unique enduring rationale and material differences among supported packages, audiences, languages, and versions; apply the retirement policy to obsolete material. Repeated examples may be necessary for standalone usability; consolidate genuinely duplicated normative instructions, not every similar explanation.

Apply type-appropriate meaning of “clean”:

- **Entry points and onboarding:** clarify who the doc is for, prerequisites, supported package/project scope, first successful path, and links to deeper guidance. Distinguish root README responsibilities from package READMEs in a monorepo; do not impose a new hierarchy.
- **Tutorials and how-to guides:** make prerequisites and steps coherent and ordered, and ensure examples are understandable and reproducible from evidence. Keep tutorials task-oriented rather than turning them into exhaustive reference.
- **API, CLI, schema, and configuration reference:** check names, parameters, defaults, units, authentication, compatibility, and version parity against authoritative source evidence. Static review is fine; do not execute commands just to prove reference text.
- **Architecture and decisions:** explain system boundaries and rationale where supported. Keep intentionally retained ADR history intact; clarify status and explicit supersession links without rewriting historical decisions as current truth.
- **RFCs, specifications, plans, and proposals:** establish intent, status, owner, and completion evidence when known; retire completed plans under the policy below rather than merely labeling them done. Do not infer completion, abandonment, or staleness from age alone; ask about conflicting status claims.
- **Runbooks and operations:** check prerequisites, impact, required permissions, safe health checks, rollback/recovery, and secret-safe examples. Report missing operational detail rather than inventing it. Never run deploy, destructive, recovery, authentication, or billable operations to verify docs.
- **Releases, migrations, and versioned/archived docs:** preserve intentionally retained release history, versioned support, and still-needed compatibility/deprecation instructions. Label applicability where retained; retire obsolete version-specific docs and completed-migration material under the policy below. Neither a newer version nor a V1 keyword alone establishes obsolescence: supported legacy integration instructions (such as approved host V1 credential import into a V2 container) remain current.
- **Security, legal, and compliance claims:** preserve disclosure, license, legal meaning, and security-sensitive material. Escalate semantic edits for authoritative human review; do not simplify away required warnings or claims.
- **Localization:** preserve translation meaning and ownership. Similar prose across languages is not proof of duplicate or stale content; do not machine-normalize or rewrite translations as ordinary copy edits.
- **Generated reference, MDX, and docs-site content:** edit the authoritative source and regenerate only through an established, approved documented workflow. Preserve frontmatter schemas, JSX/components and imports, directives, templates, fenced examples, literal fixture/example Markdown, site-specific routes/anchors, includes, redirects, and build/navigation semantics. If regeneration is not authorized or cannot be checked, report generated outputs as unverified rather than hand-editing them as if canonical.

## Retire documents without a current purpose

Retirement means **delete** unneeded Markdown files or sections, not automatically archive them, add a stale/completed label, or replace them with another report. The user-work safeguard takes precedence: evidence of obsolescence alone never authorizes deleting or overwriting untracked docs or staged/unstaged user changes; obtain specific user authorization for such retirement. Evaluate these candidates during the type-aware review:

- Session logs, event recordings, and transient progress/completion reports whose only purpose is recording a past work session. This concerns Markdown, not OpenCode session databases or runtime logs.
- Obsolete version-specific documentation and plans/reports for completed migrations that are no longer needed for current supported use.
- Feature plans/proposals whose implementation is confirmed and whose useful content is captured by maintained current docs/source.

Inspect current source/contracts, relevant maintained docs, and references to establish each candidate's status and remaining purpose; delete candidates established as unneeded after the preservation and reference repairs below. Age, a bare implementation/completion assertion, or missing inbound links is not sufficient evidence. Implementation is not a verified outcome: identify outstanding requirements and meaningful proof gaps rather than declaring success from code alone. If obsolescence or retention semantics remain uncertain, ask the human rather than delete.

Preserve or transfer the minimum still-needed operational instructions, supported compatibility, unique enduring rationale, outstanding requirements, and meaningful proof gaps/proof provenance into the appropriate maintained canonical docs before deleting the redundant remainder. Protect legal/license/security obligations, intentionally retained ADR/release/changelog/versioned-support records, and authoritative goal/proof records; do not retire these as session debris or turn a content transfer into a silent authority/status change. If their meaning or authority must change, obtain the required approval first.

Repair inbound links, navigation, and install/distribution references in the same cleanup change, including affected routes/anchors, redirects, indexes, and includes. An inbound link is a repair dependency, not by itself a reason to retain a stale document. Keep retirement evidence-supported and bounded by document family; do not delete indiscriminately by filename, keyword, age, or directory. Apply the ownership routing below to instruction-asset retirement as well as editing.

## Ownership, conflicts, and changes

For each important claim or instruction, identify one authoritative owner where appropriate: a shared project fact, role contract, reusable procedure, product/API source, release record, or legal/security authority. Link to canonical material instead of maintaining conflicting copies. Keep distinctions in scope, version, language, rationale, or audience when they are intentional. When two credible authoritative sources conflict, gather the concrete claims and paths and ask the human; do not choose a winner silently.

Agent context separation is one example of this ownership model, not the purpose of repository cleanup: shared project facts belong in applicable `AGENTS.md`, role-specific behavior belongs in that role's prompt, and reusable procedures belong in commands or skills. Do not add or require a relationship overview just because related material exists; human navigation and agent-loaded context are different. In this template, route creation, editing, or retirement of agent definitions, explicitly assigned OpenCode command/skill instruction assets (including assigned instructional references/templates), and assigned `AGENTS.md` instruction maintenance exclusively to `agent-maintainer`; do not read every agent prompt or send those files to a general documentation worker. A general documentation worker may own the remaining documentation cleanup work; executable support scripts remain implementation work, and configuration/runtime integration remains with Design. Design coordinates non-overlapping assignments; if the specialist is unavailable, report the affected instruction-maintenance portion blocked rather than use a fallback owner. Preserve complementary handoff rules, safety, approvals, permissions, model configuration, goal/proof semantics, and applicable source-versus-destination distribution boundaries.

Preserve protected records under the retirement policy above. Do not indiscriminately bulk-delete or bulk-move documentation, invent facts/examples/verification, fill template placeholders, rebaseline goal/status/proof records, or create a parallel documentation system. If a move is approved, check all inbound links, route/anchor behavior, redirects, indexes, and references before changing it. Keep the patch scoped; leave uncertain semantic changes for a human decision. On reruns, keep already-clear prose and correct links unchanged; do not recreate an equivalent overview or churn wording, links, or structure without a concrete reason.

## Validation and report

Select existing, relevant validation entrypoints based on changed file types: for example local link/anchor checks, docs-site or Markdown lint/build checks, schema/frontmatter validation, or established example checks. Use the appropriate tester for execution of validation checks (including direct URL checks) and test corrections; do not install tools, initiate network crawls, or run arbitrary commands to manufacture validation. Bounded read-only requests to inventoried URLs are direct reference checks, not permission to crawl the web or expand the inventory recursively. Do not execute deployment, destructive, authentication, or billable workflows. For generated content, use only the documented approved generation path. If no suitable check is established, say so. Keep validation claims distinct: static source review, link checks, docs build, example execution, and product behavior prove different things.

Follow applicable repository verification policy and use established checks appropriate to the changes. Do not create a test harness, tracking system, or other persistent artifacts unless requested.

Finish with a concise report of:

- changed paths and the canonical ownership decisions made;
- retired paths (or sections), brief evidence-based reasons, and still-needed content preserved or transferred, including its destination when relevant; keep this in the response, not a persistent cleanup log;
- inventory scope, classification summary, mutually exclusive coverage totals, exclusions, and uncovered groups/paths;
- conflicts escalated and unresolved semantic or ownership questions;
- relevant validation commands and exact outcomes when run by the authorized owner, plus checks not run and why;
- reference-check coverage (local paths/anchors and external URLs, including usefulness/version review), unverified paths/URLs and reasons, generated outputs that remain unverified, and other material risks.

Do not claim all docs are clean when batches remain deferred, imply external links work without checking them, or present a static review as execution or behavioral proof.
