Turn the current destination project into a reproducible, usable root `.devcontainer` setup. `$ARGUMENTS`, if supplied, are additional stack, platform, service, or version constraints; reconcile them with repository evidence and ask about actual conflicts. Where neither the user nor project evidence constrains a version, select the latest supported released version without asking the user to choose or treating that default as an enduring pin. This is an opt-in infrastructure task, not a request to initialize project goals; documentation changes are limited to the devcontainer README contract and any explicitly approved runtime-migration documentation.

During template onboarding, `/devcontainer` is the default explicit follow-up after asset installation and runtime restart. Read `docs/template-setup.md` when present and record environment decisions/status there. A skip is valid only with a concrete user-supplied reason, an evidence-based assessment against platform/security/toolchain and reproducible build/test needs, a documented alternative/tradeoffs, and user confirmation. Ask for specifics when the reason is only preference; do not reject a viable alternative arbitrarily. Until resolved, report environment readiness pending. Preserve/adapt a valid existing container; never blindly regenerate it. Keep migration, auth/session copying, and destructive changes separately approved.

Read the installed companion guide [devcontainer operating guide](../docs/devcontainer.md) and follow it. Work from the repository root where this command was explicitly invoked. Preserve user changes and inspect before editing. Invocation is explicit opt-in: it may target even the template repository; do not exclude a repository just because it is this template. Merely installing/copying this command never invokes it or generates a container.

## Workflow

**Rebuild-ready handoff is part of completion.** Before starting a replacement and before the final handoff, inspect the exact workspace/config labels and persistent-volume mounts for running owners. Gracefully stop containers created by this invocation or its validation that would retain the volume lock and obstruct the user's next editor rebuild; verify they have stopped. This includes the canonical project container started for acceptance, not just disposable test containers. Leave them running only when the user explicitly requests that handoff and the supported replacement flow has been verified to release the old owner before starting the new one. For pre-existing user containers, obtain scoped stop approval unless already granted; never stop unrelated containers. Preserve volumes and the lifetime database lock. Report the final running/stopped state and the verified next reopen/rebuild action, rather than making the human discover and repair an owner conflict.

1. Inspect the repository and existing root `.devcontainer`/Compose configuration, including tracked and untracked files. Read manifests and lockfiles, tool/version pins, CI workflows, scripts, native/system libraries, browser tooling, service dependencies, and project documentation. Identify supported development, build, lint, test, and debug workflows from evidence. Do not run goal initialization or create/edit goal files. Record missing canonical commands as “not established”; do not invent runnable strings. Update the durable setup record when present. Diagnose accessible environment failures yourself from narrowly scoped, relevant local Dev Container/build logs and existing configuration before asking for help. Follow the evidence-led repair loop in the companion guide; do not delegate environment diagnosis to the tester.
2. If the project is empty or its intended language/runtime is ambiguous, ask the human for the intended stack and any essential target platform before generating application assumptions. Otherwise proceed from evidence. Treat `$ARGUMENTS` as constraints, not evidence that a dependency is used.
3. Inspect the installed host OpenCode CLI's `--version`, help, and non-secret path metadata; determine whether it is v1 or v2 and its release channel. Separately resolve the latest supported released v2 version from authoritative v2 distribution/release information at generation time, respecting the guide's host-snapshot compatibility gate. Install `@opencode/cli` (not the v1 `opencode-ai` package), and verify the installed executable's v2 major, actual version string, and relevant help. If an artifact format requires a version string, use the selected release's version string; recording that choice does not make it an enduring default constraint. Treat configuration compatibility as an evidence-based gate: inspect exact-release docs/schema and every shared `.opencode` file it loads. If evidence says the existing files remain supported, preserve them unchanged and proceed. If an actual incompatibility exists, disclose its impact and proposed narrow migration, obtain approval before editing shared files, or report the container is not yet usable. Do not invent an isolation switch or assume the container isolates config; do not silently migrate shared config.
4. Inspect host OpenCode authentication without printing credentials, SQL rows, database contents, or tokens. Distinguish legacy host v1 auth from host v2 SQLite auth; inspect the installed runtime's documented provider metadata or supported account-list interface without initiating login. During this invocation, resolve and record one initialization mode: a supported auth import/snapshot explicitly approved for copying, or fresh no-auth initialization explicitly chosen by the user. Auth import/snapshot requires explicit human confirmation and disclosure that it may copy credentials and, for v2, sessions. Do not silently select no-auth when the user has not chosen it. Follow the guide's staging rules. If the selected auth-import path lacks established source location, provider compatibility, Docker-daemon access, or safe supported import, continue independent environment work where useful, report OpenCode blocked and the overall environment partial, and ask only for missing decision/access. Never imply authenticated-model readiness from a no-auth database.
5. Design a non-root development user, stable workspace path, project-specific durable named volume(s), correct mount ownership, reproducible toolchain, and lockfile-aware idempotent dependency bootstrap. Respect explicit user/project version constraints; otherwise choose the latest supported released versions and record the selection and resolution evidence. Install project runtime/build/lint/test/debug dependencies and browser/system dependencies only when evidenced. Add a Compose service only when the project requires a separately managed dependency. Preserve existing devcontainer files, configuration, services, and user changes: merge narrowly, explain conflicts, and obtain approval for any incompatible/destructive replacement. Never overwrite project configuration or credentials without an explicitly reviewed and approved migration merge.
6. Generate the root `.devcontainer/devcontainer.json`, Dockerfile, and only warranted lifecycle scripts/Compose files. Keep secrets out of source, image layers, logs, build arguments, and workspace; never mount the whole host home/config. Persist OpenCode data (including database sidecars) and any needed state across rebuild/recreate, without concurrent server access to the same database. Automate the selected and approved staging plus first initialization; do not leave users copy/paste commands for mechanical setup or ask them to repeat an already resolved mode/approval on rebuild. The selected path must be idempotent on the actual supported editor/CLI create and rebuild flow. Respect the lifecycle boundary: host `initializeCommand` runs before container creation, while container lifecycle hooks run inside the container. Use only an evidenced, secure editor-native host integration or fully integrated host orchestration that drives the documented creation path; do not invent a mount protocol or imply a container hook can perform host staging. If no supported automation path can meet the selected mode, leave OpenCode explicitly blocked and the environment partial rather than reporting setup success. For supported paths, serialize lifecycle, terminal, and editor initialization; safely skip an already initialized valid database; atomically publish approved staged data with mode `0600`; mark completion only after successful import/initialization. Never overwrite existing databases, sidecars, or partial state, reseed on rebuild, or treat partial initialization as fresh. Preserve and diagnose partial state rather than deleting it. A helper may report success only after the plain `opencode` executable and supported non-secret readiness checks confirm the selected initialization is ready. Distinguish a ready no-auth database from authenticated account/model readiness. Surface genuine blockers; never turn a blocked/error status into success.
7. Add or narrowly update a root README section documenting the generated setup and canonical project commands, selected tool and OpenCode versions with resolution evidence, mounts/services, chosen auth/init mode and evidence or blockers, staging/host-data disclosure and cleanup owner, volume/session persistence and backup/restore/deletion implications, and unresolved assumptions. State which setup is automated. Ask the user only for real decisions, necessary access, or login—not mechanical staging or initialization steps. Do not call OpenCode ready when its selected setup is blocked; distinguish no-auth database readiness from authenticated model readiness. Do not claim commands or checks were run unless evidenced. Preserve unrelated README content.
8. Review the diff for accidental secret/config changes and destructive operations. Have `backend-tester` independently exercise the actual generated, supported editor/CLI create and rebuild path (not just a standalone image build) and exact acceptance checks in the guide, with explicit timeouts of at least 10 minutes for build/up operations. Do not execute tests yourself. Tester owns validation only, not environment troubleshooting: if blocked, it returns concise sanitized evidence and stops; you (or a delegated Design/scout agent) independently assess the cause, make only in-scope repairs supported by the user's granted scope, then request validation again. The tester must verify plain `opencode` and supported non-secret metadata readiness, the selected approved mode's real initialization, and repeat rebuild persistence without reseeding or overwriting the initialized volume. Cover missing/unsafe auth source gates and ensure no real credentials are copied without explicit approval. Keep the report precise about unsupported or untested auth, sessions, and runtime behavior. Coordinate cleanup of validation-owned containers so no owner/lock conflict remains; never stop user work without approval or delete volumes.
