Turn the current destination project into a reproducible, usable root `.devcontainer` setup. `$ARGUMENTS`, if supplied, are additional stack, platform, service, or version constraints; reconcile them with repository evidence and ask about conflicts. This is an opt-in infrastructure task, not a request to initialize project goals; documentation changes are limited to the devcontainer README contract and any explicitly approved runtime-migration documentation.

Read the installed companion guide [devcontainer operating guide](../docs/devcontainer.md) and follow it. Work from the repository root where this command was explicitly invoked. Preserve user changes and inspect before editing. Invocation is explicit opt-in: it may target even the template repository; do not exclude a repository just because it is this template. Merely installing/copying this command never invokes it or generates a container.

## Workflow

1. Inspect the repository and existing root `.devcontainer`/Compose configuration, including tracked and untracked files. Read manifests and lockfiles, tool/version pins, CI workflows, scripts, native/system libraries, browser tooling, service dependencies, and project documentation. Identify supported development, build, lint, test, and debug workflows from evidence. Do not run goal initialization or create/edit goal files.
2. If the project is empty or its intended language/runtime is ambiguous, ask the human for the intended stack and any essential target platform before generating application assumptions. Otherwise proceed from evidence. Treat `$ARGUMENTS` as constraints, not evidence that a dependency is used.
3. Inspect the installed host OpenCode CLI's `--version`, help, and non-secret path metadata; determine whether it is v1 or v2 and its release channel. Separately resolve an exact v2 release from authoritative v2 distribution/release information at generation time, respecting the guide's host-snapshot compatibility gate. Generated artifacts must pin that exact release, install `@opencode/cli` (not the v1 `opencode-ai` package), and verify the installed executable's v2 major, exact version, and relevant help. Never use floating `latest`. Treat configuration compatibility as an early generation gate: V2 discovers shared `.opencode` files and may reject v1 agent/config frontmatter. Identify every shared file the v2 runtime loads, verify it against the exact target release schema/docs, and present the planned v2-compatible changes and host/project impact for approval before editing. Preserve an existing host v1 setup only through an isolation method documented and verified for that exact release; do not invent an environment switch or assume the container isolates shared files. If migration approval or verified isolation is absent, independent environment work may proceed, but report that the generated setup is not yet usable with V2. Do not silently migrate shared config.
4. Inspect host OpenCode authentication without printing credentials, SQL rows, database contents, or tokens. Distinguish legacy host v1 auth from host v2 SQLite auth; inspect the installed runtime's documented provider metadata or supported account-list interface without initiating login. Before staging credentials or a v2 database snapshot, obtain explicit human confirmation and disclose that it may copy credentials and, for v2, sessions. Follow the guide's staging rules. If source location, provider compatibility, Docker-daemon access, or safe supported import cannot be established, generate other environment work only if useful, report auth as blocked, and ask for missing decision/access. Never imply no-login readiness.
5. Design a non-root development user, stable workspace path, project-specific durable named volume(s), correct mount ownership, reproducible pinned toolchain, and lockfile-aware idempotent dependency bootstrap. Install project runtime/build/lint/test/debug dependencies and browser/system dependencies only when evidenced. Add a Compose service only when the project requires a separately managed dependency. Preserve existing devcontainer files, configuration, services, and user changes: merge narrowly, explain conflicts, and obtain approval for any incompatible/destructive replacement. Never overwrite project configuration or credentials without an explicitly reviewed and approved migration merge.
6. Generate the root `.devcontainer/devcontainer.json`, Dockerfile, and only warranted lifecycle scripts/Compose files. Keep secrets out of source, image layers, logs, build arguments, and workspace; never mount the whole host home/config. Persist OpenCode data (including database sidecars) and any needed state across rebuild/recreate, without concurrent server access to the same database. Preflight optional auth staging without relying on a nonexistent bind mount: choose an evidenced no-auth launch or a strategy that guarantees an existing private source path and a guard before any database-opening command. Serialize first-use import with a lock covering lifecycle, terminal, and editor launch paths. Publish staged data with mode `0600` via same-filesystem atomic placement; mark initialization complete only after successful import. Never overwrite an existing database, sidecars, or partial state, seed again on rebuild, or treat partial initialization as fresh. Preserve and diagnose partial state rather than deleting it.
7. Add or narrowly update a root README section documenting the exact generated setup and commands, evidence-backed project build/lint/test commands, pinned tool and OpenCode versions, mounts/services, auth source/mode/provider evidence and any blockers, staging/host-data disclosure and cleanup owner, volume/session persistence and backup/restore/deletion implications, and unresolved assumptions. Do not claim commands or checks were run unless evidenced. Preserve unrelated README content.
8. Review the diff for accidental secret/config changes and destructive operations. Have `backend-tester` independently perform the exact acceptance checks in the guide, with explicit timeouts of at least 10 minutes for build/up operations. Keep the report precise about unsupported or untested auth, sessions, and runtime behavior. Do not run destructive volume cleanup.
