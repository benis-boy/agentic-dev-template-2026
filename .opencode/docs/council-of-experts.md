## Purpose and scope

The proposal explores a council that can investigate opportunities, commission specialist advice, evaluate assumptions against evidence, and bring considered major-work proposals to the user. A separately named `council/Manager` would coordinate that work. The existing `Design` system would remain responsible for turning approved work into bounded implementation, coordinating delivery, and obtaining verification. Design could directly request specialist advice from the council and receive the answer without the user manually forwarding each request or reply.

The concept aims to make relevant expertise available without trimming the roster to fit an imagined salary budget, while avoiding unnecessary activation and actual resource waste (time and tokens). Members are defined by subject expertise, research responsibilities, and evidence. It seeks useful collaboration without autonomous Design↔council dispatch loops.

## When a council adds value

The intended use case is a consequential, open-ended, cross-disciplinary decision that requires integrating different disciplines and has a persistent advisory remit distinct from delivery. Relevant recommendations or constraints may conflict, but visible disagreement is not a prerequisite for value: a decision-critical evidence gap or unsupported assumption can also merit specialist perspectives. The council should add something beyond Design's existing implementation, review, and testing specialists: broad exploration and synthesis of options, not another route for ordinary implementation advice.

Routine factual lookup, a bounded technical question, or implementation work with a clear owner should normally go directly to the existing Design workflow or a well-contextualized single specialist. The council is justified only if its advice can change a meaningful decision or reduce a material blind spot. Whether it provides enough incremental value to offset coordination, latency, and model/resource costs is a hypothesis. If experience shows little benefit, prefer the simpler Design-plus-existing-specialists workflow rather than preserve the council for its own sake.

This document is general design documentation, not an agent definition, command procedure, skill, or active operating policy. The companion initializer is authored at the fixed `/init-council` path; the manager/expert IDs and shared agent-definition directory below are selected contracts for later generated outputs. Handoff shapes and lifecycle details are design contracts, not runnable syntax or claims of runtime support.

## Authored initializer and invocation boundary

This document is its canonical detailed design companion, not a second initializer procedure. The command must explicitly read this companion at runtime; mentioning it as `@path` alone does not attach or load its contents. The command body receives the user's subject through `$ARGUMENTS`; do not shell-interpolate it. This link is navigation for the human and is not itself an instruction-loading mechanism.

The authored command and this companion are source-template documentation assets, not generated council outputs. Do not treat authoring them as invocation, research for a real subject, installation of a subject council, or runtime rehearsal. When invoked in a destination project, the command is intended to bootstrap the reusable, subject-informed council through the extensive online-first research described below. Command selection occurs before execution, so bootstrap uses the existing Design coordination context and maintainer ownership; it cannot select the not-yet-authored `council/Manager`. During initialization, Design commissions `agent-maintainer` for generated definitions, without making Design a child.

The command and companion are the current authoring assets. Initialization in a destination project may later generate subject-specific definitions and knowledge notes; it does not follow that the authored assets have been exercised or that generated agents are runtime-recognized. Keep these authoring, generated-output, runtime-recognition, root-session availability, and direct-consultation milestones separate.

The generated note locations are `.opencode/docs/council/shared.md` for shared foundations and `.opencode/docs/council/<expert>.md` for each expert's current curated note. These are chosen output contracts, not files to preinstall here or a sample council. Definition/schema and runtime mechanics must not be invented where feasibility is unknown. The undefined Design decision remit and undecided goals/proof read access do not block authoring or setup: council agents must not access goal/proof records by default, and no such access is a dependency. Direct root-to-root runtime transport remains unproven; that blocks any claim that direct consultation is operational, not the authoring assets.

When invoked in a destination project, the command is intended to generate subject-specific manager/member definitions and curated knowledge notes under the user's task scope; these remain outputs of initialization, not preinstalled source assets. The shared agent-definition directory groups definitions only; it is not shared memory or a permission-isolation boundary. The companion is a distributable documentation asset and is covered by the install/update workflows' dynamic asset inventories; source-only maintainer policy and onboarding docs remain excluded by their documented distribution boundary. Do not assume that adding command or Markdown definitions changes active routing, registrations, or current sessions.

## What is known, requested, proposed, and unresolved

Keeping these categories separate avoids turning a plausible future design into a claim about current behavior.

### Confirmed current facts

- The supplied [Design definition](../agents/design.md) currently calls Design the sole primary coordinator and says it must never act as a subagent. That is current operational guidance today; future coordinated reconciliation must align routing with the selected distinct-root design while preserving Design's never-subagent rule. This document does not turn Design into a disguised child agent.
- OpenCode V2 documents primary and subagent modes, named agents, and fresh child context. Parent launch-target permissions and a child agent's own permissions are distinct concerns. A primary-capable agent is not thereby proven callable as an independent root by another primary.
- OpenCode exposes an agent's description to the model when selecting a subagent. This supports making selection-critical expertise discoverable in descriptions, but does not establish that a newly authored definition has been registered or exposed to an existing runtime/session.
- OpenCode V2 maps nested agent definition paths to namespaced IDs (for example, `.opencode/agents/team/reviewer.md` to `team/reviewer`). Thus the selected manager and expert paths/IDs above are consistent with the documented naming model; the directory itself does not imply memory or permission isolation.
- OpenCode V2 command bodies receive `$ARGUMENTS`; command agent selection occurs before execution, defaults to the current session, and `subagent: false` also selects the current session. A not-yet-authored manager therefore cannot bootstrap itself as command agent. An `@path` in the prompt does not expand into attached file content, so the command must explicitly read its companion. Do not place the supplied subject in shell interpolation.
- The cited OpenCode documentation does not establish automatic root-to-root transport or live registration of a newly created agent. Runtime recognition, session availability, and starting a separate root session must be checked rather than inferred.
- The current source repository is a reusable template with uninitialized goal-tree and proof-inventory seeds; this documentation change leaves those seeds untouched.

### User-requested direction

- Initialization should establish a distinct root-level `council/Manager` and distinct expert member agents. The manager is conceptually separate from Design, and should involve only members relevant to the task.
- Relevant expertise should be comprehensively covered; hypothetical hiring costs should not force the council to omit useful disciplines. “Complete” means adequate coverage of relevant needs, not a limitless catalog of every conceivable speciality.
- Design should be able to request in-scope specialist advice directly from the council and receive a correlated answer directly. The council can return information to the requesting Design task, but cannot dispatch or start Design work. Neither system should silently take over the other's remit.
- Hiring language may encourage quality and performance, but whether it helps is an unproven hypothesis.
- Initialization should make extensive, potentially massive online subject research its dominant effort: one user-facing setup phase may involve many searches, fetches, and parallel or sequential research passes. Local project records and implementation inform and constrain application of findings; they are not the research boundary or a substitute for broad web research. The goal is to front-load as close to all predictable, decision-relevant online research as practical for later development, curate and distribute findings to relevant members, and let members research further when their knowledge is insufficient. The user should choose among prepared A/B alternatives for consequential initialization choices while routine work proceeds independently.
- The system architect should receive focused updates about actual architecture changes without re-inspecting the entire project on every consultation. The update mechanism below is a proposal for achieving that, not an established OpenCode capability.

### Approved ownership decisions for future implementation

These choices settle design ownership, not current operating policy or implementation permission:

1. **Delegated decisions:** Design owns consequential direction and product-policy decisions only within a remit the user has approved. The exact remit is still undefined and must not be inferred from this proposal. Design escalates decisions outside it. A user-initiated task carries its stated scope; this delegation does not silently add scope, invent real spending, or expand authority. The council remains non-dispatching.
2. **Definitions and initialization instructions:** Within the user-initiated scope, Design directly commissions `agent-maintainer` to author definitions and assigned initialization command/skill instructions, without per-asset approval requests. Appropriate review remains, and the maintainer owns these assets. This is not an active role or instruction change.
3. **Knowledge notes:** `council/Manager` is the chosen ongoing publisher of curated member knowledge notes within an explicitly assigned documentation-only scope; experts research and propose sourced amendments. Keep one current note per member and merge serially from the current note while preserving supported findings. Only during initial bootstrap, before the separate manager root is available, Design may commission a bounded general documentation owner to materialize the initial researched notes; this is not a standing alternative maintenance or publishing role. Never launch `council/Manager` as a child. Notes remain derived context, not canonical project records, agent instructions, or assumed persistent memory.
4. **Runtime and activation:** When the user initiates setup, integration, or activation work, that task carries its scope; do not add a separate approval ceremony for the technical plan, configuration/integration changes, or council activation. Check technical feasibility and honor actual environment approval requirements and tool permissions; block and report unsupported actions rather than asking for a rubber-stamp approval. Activation is task-scoped and has no per-activation approval gate. This document itself does not initiate any such work.
5. **Operational routing:** `agent-maintainer` inventories and reconciles affected operational instruction/agent assets together in a coordinated change; Design integrates the cross-cutting work. Preserve distinct roots: Design is never a subagent, and neither root launches the other as a child.
6. **Relationship explanation:** Keep a concise explanation of council relationships in this general council documentation under general documentation ownership; no separate navigation guide is required. Operational truth remains maintainer-owned, and the explanation does not imply activation or a link into active instructions.
7. **Goals and proof:** The manager and members never write, update, or maintain the goals skill or goal/proof records. Their possible read-only access is undecided, not an approved dependency or mandatory initialization step. Existing Design-coordinated destination goal/proof work stays outside the council; this source template's seed records remain untouched.

### Proposed defaults for review

1. Preserve the selected concept of a separately managed root `council/Manager` alongside root `Design`, with distinct ownership. When a user initiates the relevant setup/integration task, carry its scope through implementation without another general approval gate; technical feasibility, actual environment approval requirements, and tool permissions still apply.
2. Keep `council/Manager` and Design as separate root sessions. Direct, correlated consultation requests and replies are part of the intended initial behavior; neither root is launched as the other's child. A manual user-carried exchange may be a temporary fallback if direct transport is unavailable, but it does not satisfy the requested behavior.
3. Make consultation advisory and non-dispatching. An in-scope informational request and its answer need no per-request user forwarding or additional approval. Design makes consequential direction/product-policy decisions only within the user's approved remit; its exact remit remains undefined, and out-of-remit decisions are escalated. A user-initiated task carries its scope, but does not imply a real paid commitment or authority that the user did not grant. Design sets sensible finite execution limits within that task's scope; escalate only if authority, scope, or a real paid commitment is genuinely insufficient. Route a council-originated implementation proposal through a user-carried/authorized bounded brief before Design receives it; an informational answer is not that handoff.
4. Separate roster completeness from per-task activation. Select members by relevant expertise and explain material inclusion or omission.
5. Distinguish “definition exists,” “runtime recognizes it,” and “this session can use it”; report each accurately.
6. Evaluate the hiring metaphor rather than promising that it improves outcomes.
7. Use the quality-first framing “hire broadly; commission selectively”: hypothetical salaries do not exclude relevant expertise from the roster, while actual calls, time, tools, and charges remain real and should be bounded.
8. Make initialization research-led, online-first, and mostly independent: the user supplies the subject or ambition and chooses between prepared alternatives only where a consequential preference genuinely changes the design. Give upfront research a substantial resource scope suited to covering likely implementation needs, not a token-minimizing default; do not invent a real paid commitment beyond the user's task. Do not turn setup into a questionnaire or require the user to recruit every role, choose every source, or approve each ordinary research step.
9. Treat durable expert knowledge as curated, source-backed project data refreshed incrementally when relevant—not as model memory, a per-commit council meeting, or permission to revise agent instructions.

### Deferred choices

Implementation-specific details remain open: generated definition content/schema, registration/reload procedure, technical session lifecycle, a supported direct root-to-root consultation transport with direction/correlation/finite-allowance enforcement, and roster/knowledge maintenance mechanics. The `/init-council` command name and path are fixed and authored, not deferred choices. Direct-consultation transport must be technically demonstrated before it can be claimed ready; an unsupported path is blocked and reported, not deferred as though it already works. Member roles remain advisory leaf subagents; their exact definition syntax and availability need technical confirmation. No exact permission mechanism, native recursion counter, shared-memory system, or current automated session transport is asserted here. Automatic implementation dispatch remains deferred; information replies must not be conflated with authority to start delivery.

## Two systems with separate ownership

```text
Separate root sessions; consultation is directly routed and correlated:

  Council session                         Design session
  council/Manager (root)                 Design (root)
      |                                      |
      v                                      v
  advisory leaf members                delivery specialists

  Design -- bounded consultation request --> council/Manager
  Design <-- correlated advice / blocker -- council/Manager
  council/Manager -- proposal --> User -- if approved, brief --> Design
```

The council members return analysis only to `council/Manager`; they do not call Design or its delivery specialists. A direct council reply completes the matching Design consultation; it is not a new Design task, implementation dispatch, or permission to act after cancellation. The diagram describes the desired behavior, not a claim that current OpenCode supports this transport. A user-carried exchange is only an optional temporary fallback, not the target workflow.

|---|---|---|
| User | Defines the approved remit for Design's delegated direction/product-policy decisions and decides matters escalated outside it; supplies the bounded brief for a council-originated implementation proposal; makes consequential initialization choices where prepared alternatives are genuinely needed. | User-initiated work carries its stated scope; routine in-scope research, information requests, answers, technical plan, configuration/integration work, and council activation need no additional approval ceremony. Do not infer a real paid commitment or authority beyond the request, and honor actual environment approval requirements and tool permissions. |

## Initialization and availability lifecycle

The user-facing entry point is the authored `/init-council <subject or ambition>` command. Its authoring is distinct from invocation, generated outputs, and operational readiness. Initialization should be research-led and independent by default, with user input concentrated on a small number of meaningful, prepared choices:

1. **Infer candidate council advisory scope from the given subject and project context.** Design (or an available read-only scout before the manager exists) independently identifies likely questions, project boundaries, existing architecture and constraints, and the council's advisory relationship to Design. Do not infer Design's user-approved decision remit: its exact scope is undefined. Do not ask the user to restate facts already available in the repository or select every expert.
2. **Research the subject deeply online before finalizing roles.** This should be the dominant initialization effort and may require a massive volume of online research: one user-facing setup phase can run many searches and source fetches in parallel or sequential passes, not just one query or one source. Favor authoritative current official documentation, primary research, and other high-quality sources. Front-load broadly relevant material likely to affect later implementation: alternatives and trade-offs; domain practices and failure modes; security and operational concerns; integration, compatibility, and version constraints. This is an adaptable coverage guide, not a mandate to research every category for every subject. Use local records and implementation to understand constraints, actual architecture, and applicability, but never let them replace or bound the online research. Work broad-to-deep with an explicit initialization research scope and coverage criteria. Aim to front-load as close to all predictable, decision-relevant research as practical, covering likely consequential decisions with diminishing new findings and no unreported critical gaps—not use a shallow stopping rule to save tokens, nor promise literally universal knowledge.
3. **Curate and distribute findings.** Organize shared foundations separately from domain-specific findings, cite sources and useful context, preserve cross-domain dependencies and disagreements, and avoid copying the entire research corpus into every member context. Derive and refine the relevant member roster from the evidence map; each member's remit includes doing additional targeted research when the initial synthesis or the member's current knowledge is insufficient. Report evidence coverage, key uncertainties, absent expertise, and material gaps.
4. **Prepare only consequential alternatives for the user.** Present concise A/B options with a recommendation and concrete trade-offs for choices that materially affect mandate, scope, real resource commitment, or setup direction. The user may choose either, override, or redirect; do not invent a binary where none exists. Routine research, synthesis, source selection, and other reversible in-scope decisions proceed independently. If indispensable intent cannot be inferred, ask one focused question with prepared options when possible; otherwise state the blocker rather than invent intent.
5. **Apply the user-initiated scope without a second generic approval ceremony.** The task's request carries its scope. Do not seek blanket or per-asset approval for roles, sources, ordinary bootstrap work, technical plans, configuration/integration, or activation within that scope. Check existing assets and ownership before writing; do not infer real-world spending or authority beyond the request, and honor actual environment approval requirements and tool permissions. This document itself initiates no work and grants no permission to create anything.
6. **Bootstrap through current ownership.** Design directly commissions `agent-maintainer` within the user-initiated scope for definitions and assigned initialization command/skill instructions; no per-asset approval requests are needed, and appropriate review remains. When the same task includes runtime/configuration/integration or activation, carry that scope through after checking technical feasibility and honoring actual environment approval requirements and tool permissions; do not add a separate plan-approval gate. Do not invoke a nonexistent manager during its own bootstrap or make Design a child.
7. **Report partial writes honestly.** Distinguish assets merely proposed or staged from those actually created and runtime-ready. On a retry, inspect and reconcile the selected scope; do not overwrite unrelated/existing definitions or automatically roll them back destructively. Report conflicts, unsupported mechanisms, and incomplete items; ask only for genuinely missing intent, scope/authority, a real paid commitment, or resolution of a consequential choice.
8. **Confirm availability and transport separately.** Report what was authored, whether the runtime recognizes each definition, whether a separate root session can be started, and whether a bounded consultation can be delivered to that root and returned to the requesting Design task. Selecting an agent for a task is not the same as creating or starting a separate root session. If recognition, root-session use, or direct consultation requires a reload or a new task session, state the confirmed process and blocker accurately; do not pause for another approval. Do not report the requested workflow “ready” merely because a file exists; do not quietly substitute a child agent or manual courier for unavailable transport.
9. **Begin idle.** Successful initialization establishes a researched, available roster; it does not automatically convene the whole council or launch Design. When a later user-initiated task calls for council advice, task-scoped activation is ordinary work, not a per-activation approval checkpoint.

For an existing codebase, initialization also requires at least one substantive source-aware expert. An existing architect or generalist may satisfy this if its demonstrated expertise and bounded read-only inspection are adequate; a role title, definition text, or project documentation alone is not evidence. Inspect actual source entrypoints, major modules and runtime boundaries, key flows/data, integrations, constraints, and canonical code/config navigation at a scope suitable to orient useful later advice—not the whole codebase or every expert. Record concise inspected evidence and gaps in current shared/member notes through the proper note owner; do not copy source dumps or present notes as persistent model memory. Empty/no-source projects have no code to inspect: record source orientation as pending until implementation exists, without inventing architecture knowledge. This focused source orientation complements, and never replaces, the substantial online-first subject research above.

For an existing council's refresh, reuse its current notes, supported findings, and project evidence. Reassess actual project scope and expert coverage, then research only material new, missing, changed, stale, or conflicting questions and validate relevant claims against current source/configuration as needed. This focused refresh is distinct from initial online-first research; do not repeat a large subject-wide research pass merely because the roster is being reviewed. An absent, idle, or out-of-scope manager does not publish notes by implication: identify the precise note work outstanding and provide the `/init-council <subject or ambition>` continuation, without inventing a standing Design publisher role or launching Manager as a child. Ordinary user-initiated council setup/refresh has no extra approval ceremony; runtime readiness remains separately evidenced.

This sequence distinguishes the user's meaningful scope choices, authored assets, runtime registration, and task-time activation. Its exact technical realization is deferred until checked against the actual OpenCode lifecycle, not a separate user approval. Initialization research has its own resource scope, substantial enough for the coverage objective; it is not charged against or a way to replenish a later task's finite consultation allowance. No universal numeric budget is prescribed here, and blocked sources or resources must be reported as uncovered work rather than a completed research phase.

After setup, `council/Manager` may recommend a roster or member-definition change, but it cannot edit definitions, apply mandate changes, or grant itself new authority. A bounded refresh of derived knowledge notes under its explicitly assigned documentation-only publishing scope is different from changing agent instructions and is described below. Design decides direction/product policy only within the user-approved remit; the exact remit is undefined, and decisions outside it remain for user resolution. Neither that delegation nor note publishing authorizes a real paid commitment or authority beyond a user-initiated task.

## Knowledge and agent updates

The council needs to stay current without asking the system architect to rediscover the whole project on every consultation. This is a proposed information-maintenance pattern, not a claim that OpenCode provides persistent agent memory or automatic file loading. Keep three things distinct:

1. **Stable role and instruction definition.** The member's remit, boundaries, and operational instructions are authored and changed only by `agent-maintainer` under assigned ownership. Calling prompt text a knowledge note does not make it ordinary knowledge data.
2. **Curated member knowledge note.** Each member has one current definition and one current curated note: a concise set of domain findings, the relevant project/architecture brief, known gaps and disagreements, and source links or context needed to support useful claims. Shared foundations may be referenced rather than duplicated; preserve domain-specific detail and cross-domain links. Keep enough evidence and context to reuse findings without dumping the entire research corpus into member prompts. It is derived context, not model retraining or automatic individual-agent memory.
3. **Canonical project state.** Existing authoritative project records—such as architecture decisions or design documents where they exist—and the actual relevant implementation/configuration remain the source of truth. Current notes may point to these records and summarize them, but must not create a competing architecture truth, self-authorize a decision, or override contrary source evidence. Keep proposed, accepted, planned, implemented, and verified states distinct: for example, an accepted migration plan does not mean the migration is implemented.

There is no council version-tracking system. Stable agent IDs may identify members, and initiative/request IDs may correlate consultations, but the council does not maintain definition/knowledge-note versions, revision or source-base markers, per-agent change histories, last-processed commit cursors, freshness ledgers, or required source dates. Relevant library/API compatibility versions and dates in citations remain ordinary factual context when useful; they are not council bookkeeping. Use the current definition and current curated note rather than retaining versioned snapshots.

When Design makes a material decision or implementation change, the owner of each relevant canonical project record should update it, and affected expert notes may receive concise factual updates (such as decision/status, rationale, and a useful source link). This is ordinary current-note maintenance, not a per-commit council meeting: update only affected notes, do not launch either root or wake every expert, and do not create a stale/change ledger. Sessions are task-bound: a new task starts a new session, and no pending fact or remembered context is carried into that task. For a knowledge-note update, members may research gaps and propose sourced amendments; an active `council/Manager` in scope for the current task may publish the derived-note update within its assigned documentation-only scope. If the manager is not active or in scope, report any outstanding note-maintenance need accurately; do not promise later delivery, queue the update, or automatically wake a root. Never launch the manager as a child of Design. A new task explicitly loads current persisted records and notes, then checks uncertain, stale, or conflicting areas as needed. This creates no root wake-up, queue, automatic propagation, canonical project-record editing, broader authority, or consultation-allowance reset. Material changes to mandate or role instructions follow the relevant maintainer/user boundary; Design decides direction/product policy only within the user-approved remit, whose exact scope is still undefined.

For the system-architect example, explicitly load the latest current brief and any pertinent change information for each consultation. Check only material unknowns, apparent conflicts, or areas where the provided context may be insufficient; use targeted inspection or research as needed rather than repeating full-project inspection. If the current note is missing or conflicts with canonical project records or implementation, verify the relevant part and explain the limitation. Current notes can miss changes; when confidence is insufficient, use a scoped inspection rather than automatically rebaseline the whole project. Task-relevant branch/worktree context may be supplied when it materially affects the answer, but it is not a council inventory or tracking obligation. Further online research remains appropriate for uncovered questions, new requirements, changed APIs/dependencies/security facts, stale or conflicting sources, or failed assumptions. Prepared evidence should make repeated broad research uncommon, not prohibit necessary research; that intended benefit has not been demonstrated and should be evaluated alongside answer quality and coverage.

For concurrent editorial changes, `council/Manager` handles note amendments serially within its assigned documentation-only scope, reads the current note before merging, preserves other supported findings, and reconciles contradictions against current canonical records. An earlier consultation copy must not replace a later note wholesale. This is a proposed publishing practice, not a technically guaranteed locking mechanism. Members remain advisory leaf analysts; they may research and propose evidence-backed note amendments but may not edit application code, run tests, rewrite definitions/instructions, or delegate. How current notes and relevant context are loaded and how the manager updates them remains future feasibility/design work; links alone are not assumed to load content into a fresh context.

## Roster and selective activation

The roster should be broad enough to cover the project's relevant disciplines and perspectives, not artificially reduced by hypothetical salaries. **Hire broadly; commission selectively.** Fictitious salaries do not cap relevant coverage; actual model calls, research time, tools, and charges remain real. The quality-first metaphor is a proposed framing, not proven performance advice. The roster should still be bounded by project needs: meaningful differences can justify overlap, but every imaginable specialist is not completeness. OpenCode exposes an agent's description to the model choosing a subagent, so selection-critical expertise should appear in a concise discoverable description; that does not establish definition registration or session availability.

Define each member by subject expertise, research responsibilities, evidence, reasons to consult, and relevant boundaries or limitations. Build the roster around substantive project needs and the quality and coverage of subject research, not roster size. The eventual schema is undecided; this is a conceptual inventory, not a required frontmatter specification.

Define expertise-based advisory roles, not personas. Do not create personas.

### Reassess coverage without automatic roster churn

When initializing or reassessing a council for an existing project, compare its mandates and demonstrated expertise/evidence with the project's current scope, architecture, consequential likely questions, risks, dependencies, and integrations. Identify mandates that are missing, obsolete, or inadequate and explain the concrete coverage gap and why a compatible addition or update would help. Confirm that at least one substantive expert meets the source-aware orientation requirement above. Use actual evidence, not roster size or titles. Preserve stable IDs, supported findings, and custom roles; propose rather than automatically prune, rename, or rewrite a mandate. No universal headcount applies, and ordinary refresh does not require a large research rerun.

For each task, `council/Manager` should identify the selected expertise and briefly explain material gaps or non-obvious omissions—not inventory every inactive member:

- **Why activate:** which question, risk, or decision needs the selected expertise.
- **Material gaps:** whether needed expertise is absent or unavailable. If the roster cannot cover a material need, report the gap and recommend an in-scope roster update or another path; do not imply complete relevant coverage.
- **Non-obvious omissions:** explain an omitted perspective only where its relevance is plausible and the omission could affect the decision.
- **What was asked:** the bounded question and relevant context.

Activate the smallest set that provides complete relevant coverage—not the smallest set imaginable and not the full roster by default. If an omitted perspective becomes relevant or evidence changes, the manager may recommend a new bounded consultation rather than pretend the first selection was exhaustive.

## Consultation and implementation handoffs

Two handoff types provide a simple conceptual boundary without implying that prose alone enforces it.

### Consultation: advice, no ownership transfer

```text
Design owns task
  -> bounded, correlated consultation request to council/Manager (separate root)
       -> relevant member advice
       -> council/Manager synthesis, caveats, and optional opportunity note
  <- correlated advice/blocker directly to requesting Design task
```

Design retains ownership of its user-initiated task and may launch an in-scope bounded information request without asking the user to carry it or approve activation. The request identifies the task/initiative and consultation, carries its scope, gives enough actual context to answer, and specifies a stop condition and sensible finite consultation/follow-up/attempt/time limits set by Design within that scope. Do not turn those task-specific execution limits into a numeric-budget questionnaire. One allowance applies across repeated requests and follow-ups for that task/initiative; changing request IDs, retrying, opening another session for the same task/initiative, or resetting context does not replenish it. A new task starts a new session and inherits no remembered facts or pending queue. If a task explicitly continues the same initiative, its current scope and remaining allowance must be supplied in that task's context; if they cannot be established, report the blocker rather than assume a fresh allowance.

Proposed default: collect one independent assessment from each selected member, then synthesize. Each member remains responsible for targeted research within that original assignment when prepared knowledge is insufficient; a knowledge gap may justify an initial consultation or additional research, but does not by itself justify re-asking members who have already answered.

The manager may authorize at most one focused follow-up round only when actual member conclusions or assumptions conflict in a way critical to the decision, correctness, or a serious risk. It must identify the specific conflicting claims and why they are critical, then ask only the involved relevant members for evidence or clarification. Minor differences, wording or preference, generalized uncertainty, hypothetical disagreement, or a desire for unanimity do not trigger another round. Preserve unresolved noncritical differences in the synthesis without forcing consensus. If a critical conflict remains unresolved after the permitted follow-up, return a qualified recommendation, blocker, or decision to the appropriate owner; do not continue debating.

A failed invocation may receive a bounded technical retry, not a routine second opinion. Initial calls, the permitted follow-up, and retries count against the same finite attempt/time limits Design set for the user-initiated task/initiative. If the allowance is exhausted, report the qualified result or blocker and stop; do not silently reset it or bypass it with a new ID or session. Continue only if the user supplies genuinely additional task scope or necessary authority, not to obtain a rubber stamp for ordinary bounded execution. The manager returns findings, confidence limits, sources, dissent, and a concise recommendation directly to the requesting Design task, correlated to its request. This normal answer is informational completion, not a new Design task or implementation dispatch. The manager may mention an implementation opportunity, but Design continues its existing task using or rejecting the advice; a council-originated implementation handoff requires a user-carried/authorized bounded brief.

### Implementation proposal: approval, then bounded Design brief

```text
council/Manager proposal
  -> user review / explicit authorization
       -> approved bounded brief to Design
            -> Design owns planning and delivery
            -> optional consultation returns advice only
```

A proposal is not an implementation order. It should make the desired outcome, rationale, boundaries, assumptions, and open decisions understandable to Design and the user. Once approved, the user supplies the brief to Design. Design is free to refine implementation details and verification within that approved scope, but may not treat the proposal as silently expanding its mandate or new implementation scope.

### Minimal conceptual handoff contracts

Avoid a large bureaucracy. A handoff needs to communicate at least:

| Handoff | Minimum useful content |
|---|---|
| Consultation request | Task and request references; requester and current owner; one bounded question; enough actual context and constraints; user-initiated scope; stop condition; the shared remaining consultation/follow-up/attempt/time allowance; expected answer. |
| Consultation response | The matching request reference; cited observations separated from inference and recommendation; material evidence/sources and uncertainty; disagreements or missing expertise; any optional opportunity clearly labeled as non-dispatching advice. A reply is delivered only to the requesting Design task and cannot create a new task. |
| Implementation proposal/brief | A stable initiative reference; proposed outcome and rationale; scope boundaries and assumptions; actual approval state; user-approved brief for Design, if approved. |

These are semantic contracts, not finalized typed API fields. Omit incidental metadata unless future enforcement or audit needs demonstrate it is necessary.

### Identity and continuity

A stable agent ID identifies a reusable member definition, not a versioned snapshot. Task and request references identify the work, while optional execution/session references identify an individual run. Sessions are task-bound: a new task starts a new session, and no pending fact or remembered context carries into it. Each consultation carries the current task/initiative's scope, owner, relevant context/findings, remaining question, and shared allowance. A task that explicitly continues the same initiative must carry its current scope and remaining allowance in its context; if these cannot be established, report a blocker rather than treating a new session as a reset. New tasks explicitly load current persisted records and notes; inspect relevant areas when they may be stale or conflict. IDs, filenames, and links are references only: they do not grant authority or load contents into a fresh context. Do not introduce shared memory, queues, change ledgers, version trackers, or run-log services as assumed solutions. If the direct transport cannot deliver required context or route a reply to its matching request, report a blocker rather than inventing continuity or switching to a child-agent path.

Each member response should distinguish cited observations from its inference and recommendation. `council/Manager` synthesis should retain material citations, uncertainty, and dissent rather than flattening disagreement into consensus. Independent specialist assessments are not substitutes for required verification. Council advice can inform Design but does not replace existing reviewer or tester responsibilities, required verification, or proof.

### Loop prevention: policy argument and limits

The intended safety property is not “there can never be another conversation.” It is: **an agent response cannot by itself cause an unbounded autonomous cycle of council consultation or dispatch Design implementation.** The desired graph has a Design-to-council request edge and a council-to-requesting-Design information-reply edge, but no council-to-Design implementation-dispatch edge without a user-carried/authorized bounded brief:

1. An in-scope Design consultation receives only a correlated answer, caveat, or blocker. The council cannot start or recursively consult Design. A council-originated implementation idea is only a proposal; it reaches Design as a new bounded brief only after explicit user authorization.
2. A consultation terminates with an answer, a blocker, or at most one targeted follow-up for an actual critical conflict between member conclusions/assumptions, as defined in the consultation contract. Escalate only when scope, authority, or a real paid commitment is genuinely insufficient; a task-specific allowance is set by Design and is not another user questionnaire. Advice never expands implementation scope, and work outside the user-initiated scope needs a user-carried/authorized brief.
3. Repeated Design requests, follow-ups, and retries share one finite allowance for the task/initiative. Changing request IDs, opening another session for the same task/initiative, or resetting context/model budget does not renew it. If exhausted, stop and report the result or blocker rather than silently resetting it or asking for a routine rubber stamp. A new task starts a new session and receives no remembered facts from the prior task; an explicit continuation of the same initiative must carry the current scope and remaining allowance or stop with a blocker.
4. A reply is routed only to the requesting Design task and does not renew implementation authority, become another Design task, or authorize action after cancellation. The current task scope and allowance apply throughout that task/initiative; a new task must explicitly load relevant persisted records and notes, and any continuation of the same initiative must carry its scope and remaining allowance in current context.
5. If the user initiates additional bounded work, it does not retroactively reset the same task/initiative's allowance or permit a new ID/session to bypass it. Where expected information gain is low, recommend stopping, but do not pretend the proposal forbids the user's choice. A council-originated implementation handoff still requires a user-carried/authorized bounded brief.

Thus, assuming request identity, user-initiated scope, and the shared finite task/initiative allowance are carried forward and enforced, the automatic graph permits a council-to-Design information reply but not a council-to-Design implementation dispatch. The reply closes only its matching request; it cannot create another consultation or delivery task. The finite allowance prevents an endless sequence of fresh consultation requests within one task/initiative; another session for that same work cannot reset it, and a new task has no implicit memory of the old one. This is a conditional logical argument about the intended authority graph—not runtime proof, and not protection against a user deliberately requesting more consultation or work.

Direct root-to-root consultation is an initial-implementation technical feasibility check: a supported mechanism must preserve task/initiative/request identity and the remaining finite allowance across retries and any session/context reset for that same task/initiative, deliver the request and answer to the correct roots/tasks, and enforce the reply-versus-dispatch direction boundary. A prompt saying “do not loop,” an invented recursion counter, or an assumed permission inheritance model is not adequate. OpenCode's documented agent permissions and modes do not by themselves establish this transport or context-dependent policy mechanism. If feasibility or enforcement is not demonstrated, report the blocker; a manual user-carried exchange may be an explicitly temporary fallback but does not meet the target behavior. Automatic implementation dispatch remains deferred. Technical infeasibility blocks the unsupported mechanism; it does not create an additional user-approval gate.

## Stops, failures, retries, and stale context

- **Stop/cancel:** Either side may return a clear stop, cancellation, or no-op. Preserve the original owner and do not interpret silence, partial work, or a recommendation as approval.
- **Partial failure:** Report which member responses arrived, which failed or were unavailable, whether synthesis is incomplete, and the specific gap. Do not claim complete coverage. The manager chooses whether to synthesize available evidence, retry the failed invocation within the remaining allowance, or return a blocker; Design decides how to proceed with its task. Do not ask the user to choose an ordinary in-scope recovery action. Escalate only when genuinely missing intent, authority, or consequential direction prevents proceeding.
- **Retries:** Retry only the failed bounded invocation where useful, as a technical retry rather than a routine second opinion. Reuse the same task/initiative/request identity and scope; repeated consultations, new request IDs, retries, or another session for the same task/initiative do not replenish its shared allowance or reset Design's finite effort limits. A new task has a new session and no inherited context; if it explicitly continues that initiative, it must carry the remaining allowance or stop with a blocker.
- **Conflicting advice:** Preserve material disagreement and its basis. The manager synthesizes without routine debate or manufactured consensus. Only an actual conflict critical to the decision, correctness, or a serious risk can trigger the single focused follow-up described in the consultation contract; retain noncritical disagreement without re-asking. The user or Design decides according to ownership and the task's scope.
- **Stale or insufficient context:** Each receiving root or member context must receive the exact question, relevant facts, constraints, and contract explicitly. A link or assumption that another agent has read prior prompts is not handoff context. A new task starts a fresh session: explicitly load current persisted notes and canonical project records, with no pending remembered fact from an earlier task. If context is missing, uncertain, stale, or conflicts with canonical records or implementation, perform targeted verification and explain the limitation. Include branch/worktree context only when materially relevant to the task; do not maintain a council tracking ledger. Confirm genuinely changed scope or authority with the owner before acting.
- **No useful new information:** Stop when the question has been answered, a required source is unavailable, additional activation is unlikely to change the result, or another round would merely repeat prior work.
- **Budget and effort:** Design sets sensible finite call/time/attempt limits within each user-initiated task/initiative's scope; do not ask the user to fill in a per-task limit questionnaire. Retries consume that allowance, and another session for the same task/initiative does not restore it. Do not interpret “hire broadly” or no hypothetical salary cap as unlimited model usage, tools, external purchases, or a real paid commitment not granted by the request.

## Acceptance and rehearsal scenarios

The following are normative paper walkthroughs for a hypothetical account-recovery service considering a change to how recovery records are stored. The example illustrates boundaries, not an approved product direction, vendor, architecture, research finding, or proof that any mechanism exists. Each case says what a future design should do; none was executed.

1. **Online-first initialization and concise choices.** The user supplies the recovery-service subject and available project context. The setup phase conducts many broad-to-deep online research passes before finalizing relevant expertise, using high-quality current sources and reporting what could not be covered; repository context informs applicability but does not cap the research. It prepares alternatives only if a consequential preference genuinely changes scope (for example, a still-unknown target environment); if none does, it does not invent an A/B question. The user can redirect a prepared option. Ordinary in-scope research, setup, integration, and activation proceed without per-source/per-expert or redundant approval; technical feasibility, actual environment approval requirements, and tool permissions are still checked (case 19). No source findings or coverage are presumed by this walkthrough.
2. **No circular bootstrap.** At the start, `council/Manager` does not yet exist. Design commissions `agent-maintainer` for assigned definitions and initialization instructions within the user's task scope; it does not try to consult the absent manager or become a child of it. If runtime/activation work is part of the user-initiated task, it proceeds within that scope subject to feasibility, actual environment approval requirements, and tool permissions, not an extra approval gate.
3. **Registration honesty.** Suppose the manager and member definitions have been authored, but recognition and a usable root session have not been confirmed. The report says exactly that: “authored; runtime recognition unconfirmed; current-session availability unconfirmed.” It does not say the council is ready or infer registration from files; any reload or new-session requirement must be established, not guessed.
4. **Research distribution and expertise gaps.** After research, the manager curates shared foundations and concise relevant member notes with source context, dependencies, disagreements, and known gaps. It gives each member enough supported findings to avoid needless broad repetition while leaving targeted research in the member's assignment when a question is uncovered. It selects expertise based on the actual recovery question; if the available roster misses a material discipline, it reports that gap rather than claiming complete coverage. This scenario supplies no invented research conclusions.
5. **Research reuse in later work.** Design asks whether a particular recovery-record change is compatible with a stated constraint. The manager and relevant member first receive the current note and pertinent project context; they reuse what answers the question and research only a missing, conflicting, unreliable, or changed fact. A changed API, newly discovered requirement, or failed assumption triggers focused research. The answer may say the prepared evidence is insufficient. Whether this actually makes broad repeat research rare without reducing quality is an evaluation question, not a result asserted here.
6. **Selective activation.** A routine internal storage refactor with no unresolved cross-disciplinary decision stays in the ordinary Design workflow. If the request instead changes the user-facing recovery journey, the manager may select recovery/security expertise and accessibility expertise where the concrete question makes it relevant, and state material omissions. It does not wake the whole roster or list every inactive member.
7. **Incremental architect update.** The canonical architecture record says a recovery-record migration is accepted and planned, while the implementation has not changed. The architect receives that current record and relevant factual change context, checks only material unknowns, and does not describe the migration as implemented. If an expert proposes a sourced note amendment, a manager already active and in scope for the current task may merge it into the current note. If idle or out of scope, no root is awakened and no later delivery is promised or queued; report any outstanding note-maintenance need accurately. A new task starts a new session, loads current persisted records/notes, and checks uncertain or conflicting areas; no pending fact is remembered from this task. Neither path proves complete change detection or eliminates targeted inspection when context is uncertain.
8. **Current-note conflicts and concurrent edits.** One proposal would add supported recovery-compatibility findings while another would add independently supported operational findings. The manager reads the current note before publication, merges both supported amendments serially, and preserves existing supported material; it does not replace the note with an earlier consultation copy. If a note conflicts with a canonical record or implementation, it verifies that relevant point and reports unresolved ambiguity rather than choosing by recency alone. Serial merging is editorial intent, not a lock or proof of race-free publication.
9. **Targeted knowledge maintenance without root dispatch.** After Design makes a material, accepted recovery-architecture change, the owner updates the relevant canonical record. A manager already active and in scope for the current task can publish a concise affected-note update. If it is idle or out of scope, do not promise later delivery or queue the update; report outstanding maintenance need rather than implying it was delivered. A new task starts a new session and explicitly loads current persisted records/notes; no pending fact carries forward. No expert is convened, no allowance is replenished, and Design work is not restarted.
10. **Knowledge versus instructions.** An expert's sourced proposal may amend its current derived knowledge note through a manager already active and in scope for the task. If it instead recommends changing the expert's remit or instructions, that is referred to maintainer-owned definition work. A proposed architecture choice remains distinct from a canonical accepted decision, and an accepted plan remains distinct from implemented state.
11. **Direct consultation preserves ownership.** Design sends a bounded recovery question directly to the separate manager root; selected members return advice to that manager, which synthesizes a response correlated to the same Design task. Design retains its task and decides what to do with in-scope advice; no user courier is part of the intended behavior. Neither root launches the other as a child. The relationship is explained here; the documentation link does not imply active runtime instructions. These are desired semantics; available transport is unproven.
12. **Proposal requires approval.** The council proposes a bounded recovery-workflow change with rationale, scope, assumptions, and open decisions. The proposal remains unapproved and Design does not begin that new implementation. Only after the user explicitly approves a bounded brief does Design receive and plan that work; an approval does not silently enlarge Design's undefined decision remit or authorize unrelated scope.
13. **Root/task routing and no reverse dispatch.** If Design has recovery consultations A and B, an answer for A is delivered only to A's requesting task, not B or a new Design task. The manager cannot recursively call Design, launch it as a child, or turn a recommendation into delivery. If A is canceled before a reply arrives, that reply is not permission to continue or act; it is discarded or reported as late/canceled according to the eventual transport. Correct routing and cancellation enforcement still require runtime evidence.
14. **Shared consultation allowance.** Design sets sensible finite limits within the user-initiated task/initiative scope; this paper case assigns no invented count and does not ask the user to choose one. Repeated requests, any permitted critical-conflict round, and bounded technical retries all count against that same allowance. A new request ID or another session/context reset for the same task/initiative cannot replenish it. If the remaining amount cannot be carried and established after a reset, stop and report the qualified result or blocker rather than assume a fresh allowance. New tasks start in new sessions and do not inherit pending facts or remembered context; an explicit continuation of the same initiative must carry the remaining allowance in current task context.
15. **Unavailable transport.** If discovery cannot demonstrate a supported separate-root request/reply path with correct task routing, sufficient context, cancellation behavior, and shared-allowance enforcement, the report names the missing capability and blocks direct consultation as not ready. It does not substitute a child-agent path, pretend a manual user-carried exchange meets the requested behavior, or claim runtime support from this document.
16. **Synthesis-first consultation.** Each selected member first gives an independent assessment and may research within that original assignment. A single member's uncertainty or missing fact leads to targeted research, not a second round asking everyone again. If actual assessments conflict on a point critical to recovery correctness or a serious risk, the manager identifies those claims and asks only the involved members for one focused evidence/clarification round. It then preserves any unresolved conflict in a qualified answer or blocker; minor differences remain visible without debate or forced consensus.
17. **Bounded effort.** Broad initialization research has its own substantial coverage scope and is not charged against or used to replenish later task consultation allowance. Design sets sensible finite call, retry, tool, and elapsed-time limits within each user-initiated task; no numeric choice is a user questionnaire. “Hire broadly” grants no real paid commitment beyond the request. If sources or capacity block coverage, the manager marks the research incomplete. No fixed token count or numeric allowance is invented here.
18. **Goals and proof stay outside council ownership.** Suppose a council finding suggests a product-outcome or verification change. The manager returns it as advice to Design; neither the manager nor members ever write, update, or maintain the goals skill or goal/proof records. They do not read these assets by default either: possible read-only access remains undecided and is not required for setup. Design handles any warranted record changes through its ordinary destination-project workflow outside the council. This compendium does not populate or alter the source template's seed records.
19. **User-initiated setup and activation, with feasibility checks.** If the user initiates council setup or a task that includes runtime/configuration/integration/activation, the task carries its scope: Design commissions implementation specialists for executable integration and configuration, and `agent-maintainer` for affected definitions and assigned instructions. Design checks how separate-root selection, registration, routing, context, and allowance handling work, and proceeds with supported changes without a separate technical-plan or per-activation approval. There is no redundant user confirmation step after feasibility findings. Unsupported mechanisms are blocked and reported, not converted into an approval question. Actual environment approval requirements and tool permissions remain binding. This worked scenario itself performs no setup, integration, or activation.
20. **Partial failure without routine user intervention.** One selected member responds and another invocation fails while allowance remains. The manager assesses whether the missing expertise is essential: it may perform a useful bounded technical retry, synthesize sufficient available evidence with the gap disclosed, or return a blocker if a sound answer is not possible. Design continues what can responsibly proceed within scope, without asking the user to choose retry versus continue. Neither role invents the missing findings or silently increases the allowance; genuinely missing intent or authority is escalated rather than assumed.

These walkthroughs resolve intended behavior on paper only. Before any future runtime claim, prepare and execute a separate validation plan against the actual installed OpenCode behavior covering definition authoring/recognition/session availability, separate-root selection, direct request/reply routing and cancellation, context and allowance continuity/enforcement across retries and resets, current-note loading and serial publication behavior, and actual research-reuse quality/cost. ## Limitations and decisions needed

The proposal does not settle how the requested separate root is selected and started in a supported runtime, how multiple primary agents coexist with current configuration, how definitions become available in-session, or whether a supported transport can enforce correct direct consultation routing and finite allowances. That is an initial-implementation technical feasibility check, not a user-approval gate; unsupported behavior must be blocked and reported. Loading current notes and relevant context, and publishing updates without losing supported findings, also need a future implementation design; no reliable mechanism is claimed here. Notes can be incomplete or stale, so uncertain context calls for focused verification rather than a claim of certified currency. This concept does not prescribe a technical policy engine, durable request store, or always-on shared-memory service; the logical safety argument depends on maintaining request/task continuity and the allowance across retries and session resets for the same task/initiative, and is not runtime proof or a hard security boundary. Sessions are task-bound and a new task does not inherit remembered facts. An explicit continuation of the same initiative must carry its current scope and remaining allowance in task context. An optional temporary manual exchange does not satisfy the direct-consultation target.

5. How the initiative/task-level consultation allowance and request correlation remain enforced across repeated requests, follow-ups, retries, new IDs, and session/context resets. If this cannot be demonstrated, direct consultation is blocked; do not present manual forwarding as fulfillment.
6. Design-set finite initial/member, follow-up, retry, and total attempt/time limits within the user-initiated task/initiative scope, including the stop condition and how an exhausted allowance is reported rather than silently reset or turned into a routine approval request.
7. A feasible way to load the current notes and relevant project/change context for a consultation, and let `council/Manager` publish updates to the current note within assigned documentation-only scope while preserving supported findings and deferring to canonical project records. Do not add note revisions, source-base markers, branch/worktree inventories, freshness dates, or stale-status ledgers. When context is uncertain, targeted verification remains the fallback; automatic full-project rebaseline is not required.

These are technical feasibility and implementation requirements for a later user-initiated task—not approval gates and not requirements that the user approve a technical plan. The authored command and companion do not create or activate a council merely by existing.

### Deferred beyond the initial implementation

- Automatic implementation dispatch from the council to Design remains deferred; the user-carried/authorized bounded-brief path is the target. This is distinct from the direct informational request/reply transport, which has an initial-implementation technical feasibility requirement. No implementation handoff is implied by successful consultation.
- Comparative evaluation is needed **before claiming that the council or hiring metaphor improves outcomes**, but is not a prerequisite for an approved bounded pilot. Future comparison should use the fair conditions described above and be allowed to conclude that the simpler Design-plus-specialists workflow is preferable.
- The criteria above establish a minimum coverage reassessment, not automatic roster maintenance or a complete mandate for every future project. Any later expansion of real-resource budgets remains open.

The initialization command and its canonical companion are authored reusable source assets. This authoring does not pre-install council agents or prove a root-to-root transport. The broader council remains a target design until initial-implementation feasibility is addressed: direct informational consultation is desired but unimplemented and unproven; automatic implementation dispatch and claims of benefit remain deferred.
