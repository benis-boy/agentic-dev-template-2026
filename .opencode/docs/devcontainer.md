# Reusable Devcontainer Command Guide

This guide supports the explicitly invoked `/devcontainer` command. It adapts the repository where it is invoked, even if that repository is this template; merely installing or editing the reusable template never invokes the command or generates a container. It does not initialize goals or promise that host authentication is portable. The target project owns generated runtime configuration and README documentation.

For onboarding, this is the default explicit environment step after template assets are installed and the runtime restarted. Read/update `docs/template-setup.md` if present. Skipping requires a concrete user-supplied reason assessed against platform/security/toolchain constraints and reproducible build/test needs, a documented alternative and tradeoffs, and user confirmation. If the stated reason is only preference, ask for specifics; assess a viable alternative fairly. Keep unresolved decisions pending. Inspect and preserve a valid existing container; adapt reviewed gaps only, never regenerate blindly. Asset installation never invokes this command, installs/migrates runtimes, stages auth, copies sessions, or creates container files. Runtime migration, credential/session copy, and destructive replacement require separate approval. During `/devcontainer`, resolve the user's real initialization decision once; automate its approved setup on the supported create/rebuild path rather than leaving mechanical OpenCode initialization to the human. Do not repeat approval/mode questions at each rebuild.

## Inspect and design

- Inspect existing `.devcontainer` and Compose files before editing; preserve them and merge narrowly. Inventory manifests, lockfiles, version pins, CI, native libraries, browser tooling, services, and canonical build/lint/test/debug commands. Ask rather than invent a stack for an empty or ambiguous project.
- Generate root `.devcontainer/devcontainer.json`, Dockerfile, and only necessary scripts/services. Honor explicit user/project version constraints; otherwise select the latest supported released versions for the runtime, package managers/toolchains, and OpenCode. Resolve OpenCode's selected version from authoritative v2 release/distribution information when generating. V2 distribution is `npm install -g @opencode/cli` (not v1 `opencode-ai`); verify the installed executable's actual version string, v2 major, and relevant help. If an artifact format requires a version string, use the selected release's version string; this records the chosen resolution, not an enduring default pin. Do not ask the user to choose a version when no constraint or actual compatibility conflict exists. Do not install or download OpenCode merely while editing/installing the reusable template.
- **Gate usability on evidence of compatibility, not assumed incompatibility.** V2 discovers shared `.opencode` files. Identify the selected target release and actual installed runtime version; inspect that release's compatibility docs/schema and every shared file it loads. If exact-release evidence says the existing files remain supported, preserve them unchanged and proceed without an unnecessary migration or host-runtime isolation change. If an actual incompatible file/field/plugin/API is found, disclose its impact and proposed narrow migration, obtain approval before editing shared files, and otherwise report that the container runtime is not yet usable. Do not invent an isolation switch, silently migrate, or weaken policy.
- Use a non-root dev user, fixed workspace path, proper ownership for mounted volumes, and a lockfile-aware, idempotent bootstrap. Install runtime, build, lint, test, debug, native, and browser dependencies only when project evidence requires them. Add a Compose service only for an evidenced external project service.
- Give OpenCode a uniquely named, stable per-project Docker named volume for its data database (including SQLite WAL/SHM sidecars) and any required state. Match XDG/`OPENCODE_DB` configuration to the persisted path. Initialize ownership safely; enforce one active container owner for the volume for the entire container lifetime, while allowing ordinary clients in that owner container to use OpenCode's managed shared service. Reject a second container before any database access. Never use anonymous storage or destructive `down -v` cleanup. Container rebuild/recreate must not seed over existing container data. Never mount the whole host home or OpenCode config.
- Treat OpenCode initialization as generated setup, not a manual README procedure. Resolve and record the mode during `/devcontainer`: auth import/snapshot only with explicit approval to copy credentials (and v2 sessions where applicable), or fresh no-auth initialization only when explicitly chosen. Never silently switch a failed/unsupported import to no-auth. Automate the selected mode on the actual supported editor/CLI create and rebuild path; it must be idempotent, preserve a valid initialized volume, and not ask the user to repeat an already-made choice. No-auth is a real CLI/database initialization and readiness check, not a marker-only shortcut. A supported auth import is ready only after its verified import and supported non-secret account/provider checks succeed. Database readiness in no-auth mode does not mean authenticated-model readiness.
- Respect actual lifecycle boundaries: host `initializeCommand` executes before container creation; container `postCreateCommand`/`postStartCommand` execute inside the container. Use an evidenced secure editor-native host integration or fully integrated host orchestration driving the documented creation path to stage host data; do not prescribe an unverified mount protocol, pretend an in-container hook can access host state, or claim direct editor readiness for unsupported clients. If the selected mode cannot be automated in a proven supported path, report OpenCode blocked and the environment partial; do not report successful setup or make a user perform mechanical copy/init commands. Normal project development must remain available when optional auth is unavailable.
- Serialize initialization paths and validate the selected state before any ordinary database-open path. A helper can report setup success only when the plain `opencode` executable is usable and supported non-secret readiness metadata confirms the selected mode. It must safely skip a complete valid initialized database; never overwrite an existing database, sidecars, credentials, sessions, or partial state; preserve and diagnose incomplete state; and only mark success after the actual import or fresh no-auth initialization succeeds. Never mask a genuine blocker/error as success, including by accepting a blocked status code. Keep credentials out of logs/source/build/repo and do not use broad permission changes or auth during image build.

## Autonomous environment diagnosis and bounded repair

The invoked `/devcontainer` agent owns environment diagnosis and ordinary in-scope repairs; this work is independent of tester validation. Aim to leave the generated environment complete and ready after the user's selected and approved setup, rather than stopping at the first recoverable build, corporate network, trust, initialization, or rebuild failure. Do not ask the user to say “keep going,” locate accessible logs, repeat an already supplied path, approve an already approved choice, or point out relevant existing local examples. Ask only for a genuine decision, access, or approval that cannot be established safely from available evidence.

- Start with read-only, narrowly targeted inspection of accessible local Dev Container/container/build logs, the relevant configuration and scripts, and the first causal error (not merely downstream failures). Sanitize evidence; report the pertinent error and source, never dump logs, environment/credential values, database contents, or broad command output. Inspect host CA/proxy configuration only for relevant names, paths, and public-certificate metadata; never print or search credential-bearing environment values.
- Once evidence indicates a network/TLS issue, inspect only relevant referenced or nearby known local Dev Container examples and base-image sources, plus the specific installed toolchain's trust behavior. Reuse an already user-approved, enterprise-managed public root CA and its established installation pattern only within the project/use covered by that approval, and when the certificate identity, fingerprint, and source agree with existing evidence. Record the corporate-specific adaptation and make trust installation reproducible before network-dependent build steps and at runtime where needed. An approved public root certificate may be copied into generated project files when necessary; private keys, proxy credentials, netrc files, and other authentication material are never copied into source, image layers, logs, build args, or workspace. Use a narrowly scoped external/private build secret only if essential and supported, without persisting it in the image.
- This source checkout's two existing, user-approved public root CAs and their automated trust installation are an approved baseline here: preserve and maintain that setup, verify the relevant certificate identity/fingerprint against available evidence, and do not ask again to reuse or mechanically install those exact certificates for the already-approved use in this checkout. The approval applies only to the matching approved project/use and exact material; it does not automatically transfer to a new destination or authorize a different/new authority, material with unclear provenance, or a trust-policy change. Obtain the destination project's approval before using these certificates there unless an approval expressly covers that destination and use.
- Install trust in the system store and the relevant Node/toolchain-specific stores or explicit CA variables where evidence requires them. Do not assume OS trust automatically covers Node or every package tool. Never bypass TLS verification with `NODE_TLS_REJECT_UNAUTHORIZED=0`, `strict-ssl=false`, equivalent flags, or by trusting an intercepted peer certificate. Do not blindly trust an unknown interception CA or import a broad host bundle when its policy/provenance is unclear. Request explicit approval for a new destination/use unless it is already covered, as well as for a genuinely new trust authority, unverifiable certificate provenance, or a step beyond mechanical copying of a verifiably approved public certificate within its approved project/use. If safe provenance cannot be established, stop that trust change and explain the specific blocker.
- Tighten permissions on a regular credential file only when its owner and identity are unambiguous, it is not a symlink, and the change is least-privilege and non-destructive within the user's approved staging scope. Reject ambiguous ownership, symlinks, or any operation risking data loss. A prior approval is specific to its identified material and scope; never treat it as blanket authorization for other credentials or developers.
- Use relevant existing configuration as evidence for a narrow repair, not as permission to copy entire images, services, authentication mounts, or unrelated configuration. Make a bounded number of reasonable repair/rebuild attempts, each driven by new evidence; do not loop indefinitely, install global dependencies, initiate login, or make unrelated changes. Preserve host data and user changes. Manage only validation-owned containers; do not stop unrelated/user containers without approval. If genuinely blocked, request the smallest concrete decision or access item only after available evidence and safe in-scope repairs are exhausted.
- A tester's validation failure is evidence, not a troubleshooting assignment: the tester reports concise sanitized first-cause evidence and stops. The Design agent coordinates independent investigation within the granted user scope; a delegated scout may perform read-only discovery and report evidence, but does not repair. The assigned implementation owner applies supported in-scope repairs and reports evidence back to Design; Design requests tester revalidation. Never ask the tester to explore the host, discover corporate setup, or repair environment configuration.

## Authentication: inspect, disclose, and gate

Inspect CLI version/help and documented non-secret path metadata only; v2 `opencode debug paths db|data|state|config|cache` reports paths without starting a server or opening the database. Ensure pre-initialization metadata calls cannot create persistent XDG directories or leave state that blocks fresh-volume setup; use disposable private XDG roots for executable version/help and report known persisted debug paths without opening the database. Account/provider metadata must come from the installed version's supported interface and must not reveal credentials. Account presence is not proof every provider can import or authenticate. Before staging either auth format or a v2 DB snapshot, get explicit human confirmation and disclose that the copy can include credentials and, for v2, host sessions. A SQLite snapshot is not an official auth-import guarantee.

Resolve the host's actual data location, including `XDG_DATA_HOME` / `OPENCODE_DB` overrides, release channel, platform (including Windows), and Docker daemon locality. Do not bake a developer home path into shared files. Any bind source must exist and be accessible to the Docker daemon. A preflight/lifecycle step must handle missing or inaccessible optional staging without breaking an otherwise usable container; report auth blocked and ask for the required access/path instead. Never login silently.

- **Host v1:** locate its existing `auth.json` without displaying it. If the exact container v2 release documents support for the legacy migration and provider, stage mode `0600` into the container-owned v2 data directory **before its first-ever database open**. Avoid bind-source assumptions: lifecycle must not depend on mounting a host path that might not exist. Use the verified host preflight for the approved auth-import mode or, only when explicitly selected, the verified fresh no-auth mode; ensure plain `opencode`, terminal, editor, and lifecycle launch paths share the appropriate startup guard. Serialize the entire first-use initialization/import under a lock; use same-filesystem atomic publication and write an initialized marker only after a fully successful import. If there is existing DB, sidecar, marker, or partial state, never overwrite or reseed; preserve and diagnose it and block unsupported import/recovery. Never delete the database or assume migration reruns. Verify provider via supported non-secret metadata; legacy migration does not prove every provider is supported. Document staging cleanup responsibility.
- **Host v2:** never bind a live host database into a second server, raw-copy a running SQLite database/WAL, or open a snapshot using a release with unknown/older schema compatibility. A snapshot is allowed only after explicit confirmation to clone host sessions and credentials. Prefer the exact same v2 release; otherwise require documented and tested forward compatibility, using a disposable private copy. Use a supported SQLite online-backup API/tool to create a consistent snapshot in a private mode-`0700` staging directory outside workspace/build context; protect snapshot as mode `0600`. Mount read-only and seed once into a dedicated persistent volume using the same locked, atomic, success-marked initialization. Never assume this snapshot is an official auth import or invent a credential export/edit. Do not overwrite an existing DB, sidecars, or partial state. If exact compatibility is unknown, stop snapshot import; do not open host data blindly.
- A snapshot is a one-time clone, not live/two-way credential sync. Later host auth changes do not propagate. Never reseed/overwrite container sessions on startup/rebuild. Any approved refresh requires a separate reviewed, supported procedure preserving sessions and credentials; otherwise report refresh unsupported. Repeated starts and rebuilds with the same data volume must leave its identity/data untouched.

If the selected auth-import source is missing/unsafe, provider support is uncertain, the daemon cannot access the source, or safe snapshot/import cannot be verified, keep normal container/project development usable and keep host DB untouched. Report OpenCode blocked and the environment partial, with no success masked by a status fallback. Ask only for the necessary decision/access, never for mechanical staging or initialization. Do not call an explicitly chosen no-auth mode blocked merely because no credentials exist; report its database readiness separately from the absence of authenticated model access. Never put credentials in repo files, image layers, logs, build args, or broad host mounts.

OpenCode v2 stores provider accounts in SQLite by default under `~/.local/share/opencode/opencode.db`; actual paths may change with XDG, `OPENCODE_DB`, or release channel. Supported legacy auth can be imported during database migration; later SQLite updates are not written back to `auth.json`. Do not assume compatibility or incompatibility from the v1 syntax alone: inspect matching v2 compatibility docs/schema and loaded shared files. Preserve supported existing files unchanged. Migrate only an evidenced incompatible project runtime config after separately reviewed approval. Do not silently edit shared v1 config or weaken policy. If a real incompatibility is not approved for migration, report that blocker even if v2 installation is generated.

## Persistence and generated README contract

Document exact start/reopen/rebuild and canonical project build/lint/test commands; which OpenCode setup steps are automated on the supported create/rebuild path; selected tool and OpenCode versions with resolution evidence and any user/project constraints; workspace path, services, mounts and ownership; chosen auth/init mode, source/provider verification, and blockers; snapshot host-data disclosure, external cleanup owner, and one-time refresh limits; and how to back up and restore the persistent data volume. List only actual user decisions, access, or login needs as manual actions—not mechanical initialization. Clearly distinguish no-auth database readiness from authenticated model readiness and blocked OpenCode from a ready environment. Version strings required by artifact formats record the chosen releases for this generated setup, not enduring defaults. Explain that container deletion/rebuild retains the named volume, while deleting that volume loses OpenCode sessions and credentials. Never suggest `docker compose down -v` or any volume deletion as routine cleanup. Session identity depends on keeping the same project workspace path and persisted OpenCode DB; concurrent servers must not open the same DB.

Generated README statements must distinguish observed facts, generated behavior, human decisions, and checks actually run. Include the evidence for dependencies and canonical commands; list blockers and unsupported/untested claims plainly. Do not claim auth reuse, session persistence, or a successful build without acceptance evidence.

## Independent validation

### Rebuild-ready handoff

Treat release of the old container's volume ownership as part of the create/rebuild workflow, not a manual follow-up. Inspect exact workspace/config labels and volume mounts before replacement and final handoff. Gracefully stop invocation/validation-owned containers that would obstruct the next editor rebuild, including a canonical project container started for acceptance, and confirm the stopped state. Do not leave such an owner running merely because acceptance passed. A running-container handoff requires an explicit user request and evidence that the supported replacement flow stops the old owner before starting its replacement. Scope any stop to the identified container; pre-existing user work needs stop approval unless already granted. Never delete volumes, weaken the lifetime lock, or indiscriminately stop Docker containers. The final report must state whether the project container is stopped or running and how the user can reopen/rebuild without a leftover-owner conflict. Verify the replacement handoff, not just repeated CLI startup against an already running container.

Delegate to `backend-tester`; implementation agents do not execute these acceptance checks. Tester validates the actual generated, supported editor/CLI create and rebuild flow, not a standalone image build alone, and reports concise, sanitized first-cause evidence then stops if blocked. The Design agent coordinates environmental diagnosis; a delegated scout is limited to read-only discovery, while the assigned implementation owner performs any supported in-scope repair. After that evidence-based repair, delegate revalidation. Use the selected release's matching schema and supported devcontainer CLI/config validation; build and start the destination container with explicit timeouts of at least 10 minutes; verify exact installed OpenCode v2 version; and run evidenced project build, lint, and tests. Inspect supported auth/provider metadata without login, credential output, or inference. For the explicitly selected mode, execute its real automated initialization and prove setup success requires plain `opencode` plus supported non-secret readiness checks. Test no-auth readiness separately from authenticated-account/model readiness. Exercise missing/unsafe optional auth source without breaking ordinary project development; verify blocked status is visible rather than converted to success. Confirm version/help/path metadata leaves the persistent volume unchanged. Verify a second container using the same volume is rejected before database access while ordinary CLI clients in the owning container can use its managed shared service. Verify an unknown/incompatible snapshot release is rejected before host DB access, and test initialization under concurrent launch attempts, repeated starts, pre-existing DB/sidecars, interrupted/partial state, and rebuild using the same initialized volume without reseeding or overwrite. Verify no real credentials are copied absent approval. Where supported without paid inference, create/list a harmless session using actual documented help/API, record its stable ID, workspace path and provider evidence, rebuild/recreate without deleting volumes, then confirm the same session ID, project path and provider remain. If harmless session creation/listing is impossible without inference or unsupported interfaces, say so and report persistence untested—never fabricate proof. Coordinate cleanup of tester-owned containers so volume ownership/locks are released; never stop user work without approval and never delete Docker volumes.

For legacy auth, expose the guarded launcher as the normal `opencode` executable on PATH (including interactive terminals, lifecycle scripts, and editor tasks); keep the underlying binary in a private implementation path. This is startup ordering, not an agent permission restriction. Also verify that an unavailable required source leaves project development usable but blocks OpenCode setup and plain `opencode` before any unsupported DB open; restoring the source lets automated seeding proceed. Cover an already-opened database separately: preserve it and report blocked unless a supported recovery/import has been verified. For a chosen no-auth mode, verify the converse: automated initialization/readiness succeeds without host auth and makes no authenticated-model claim.
