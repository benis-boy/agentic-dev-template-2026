# Reusable Devcontainer Command Guide

This guide supports the explicitly invoked `/devcontainer` command. It adapts the repository where it is invoked, even if that repository is this template; merely installing or editing the reusable template never invokes the command or generates a container. It does not initialize goals or promise that host authentication is portable. The target project owns generated runtime configuration and README documentation.

## Inspect and design

- Inspect existing `.devcontainer` and Compose files before editing; preserve them and merge narrowly. Inventory manifests, lockfiles, version pins, CI, native libraries, browser tooling, services, and canonical build/lint/test/debug commands. Ask rather than invent a stack for an empty or ambiguous project.
- Generate root `.devcontainer/devcontainer.json`, Dockerfile, and only necessary scripts/services. Pin runtime, package managers/toolchains, and the current actual OpenCode v2 release exactly. V2 distribution is `npm install -g @opencode/cli` (not v1 `opencode-ai`); resolve the exact current version from authoritative v2 release/distribution information when generating, never float `latest`, and verify executable version, v2 major, and help. Do not install or download OpenCode merely while editing/installing the reusable template.
- **Gate usability on config compatibility before generation.** V2 discovers shared `.opencode` files and can reject v1 agent/config frontmatter. Inspect the exact release schema/docs and every shared file it loads; propose the required v2-compatible config, permissions, agent fields, and plugin changes and disclose host/project effects. Get approval for shared migration. Preserve an existing host v1 runtime only through an isolation method documented and verified for the exact release; do not invent an environment switch or assume the container isolates config. If approval or verified isolation is unavailable, independent container work may be generated, but report that its V2 environment is not yet usable. Do not silently migrate, weaken policy, or leave an unexplained mixed-version config.
- Use a non-root dev user, fixed workspace path, proper ownership for mounted volumes, and a lockfile-aware, idempotent bootstrap. Install runtime, build, lint, test, debug, native, and browser dependencies only when project evidence requires them. Add a Compose service only for an evidenced external project service.
- Give OpenCode a uniquely named, stable per-project Docker named volume for its data database (including SQLite WAL/SHM sidecars) and any required state. Match XDG/`OPENCODE_DB` configuration to the persisted path. Initialize ownership safely, keep one server at a time on the database, and never use anonymous storage or destructive `down -v` cleanup. Container rebuild/recreate must not seed over existing container data. Never mount the whole host home or OpenCode config.

## Authentication: inspect, disclose, and gate

Inspect CLI version/help and documented non-secret path metadata only; v2 `opencode debug paths db|data|state|config|cache` reports paths without starting a server or opening the database. Account/provider metadata must come from the installed version's supported interface and must not reveal credentials. Account presence is not proof every provider can import or authenticate. Before staging either auth format or a v2 DB snapshot, get explicit human confirmation and disclose that the copy can include credentials and, for v2, host sessions. A SQLite snapshot is not an official auth-import guarantee.

Resolve the host's actual data location, including `XDG_DATA_HOME` / `OPENCODE_DB` overrides, release channel, platform (including Windows), and Docker daemon locality. Do not bake a developer home path into shared files. Any bind source must exist and be accessible to the Docker daemon. A preflight/lifecycle step must handle missing or inaccessible optional staging without breaking an otherwise usable container; report auth blocked and ask for the required access/path instead. Never login silently.

- **Host v1:** locate its existing `auth.json` without displaying it. If the exact container v2 release documents support for the legacy migration and provider, stage mode `0600` into the container-owned v2 data directory **before its first-ever database open**. Avoid bind-source assumptions: lifecycle must not depend on mounting a host path that might not exist. Use a verified preflight/no-auth strategy or guarantee the source path exists privately; ensure plain `opencode`, terminal, editor, and lifecycle launch paths share a startup guard. Serialize the entire first-use initialization/import under a lock; use same-filesystem atomic publication and write an initialized marker only after a fully successful import. If there is existing DB, sidecar, marker, or partial state, never overwrite or reseed; preserve and diagnose it and block unsupported import/recovery. Never delete the database or assume migration reruns. Verify provider via supported non-secret metadata; legacy migration does not prove every provider is supported. Document staging cleanup responsibility.
- **Host v2:** never bind a live host database into a second server, raw-copy a running SQLite database/WAL, or open a snapshot using a release with unknown/older schema compatibility. A snapshot is allowed only after explicit confirmation to clone host sessions and credentials. Prefer the exact same v2 release; otherwise require documented and tested forward compatibility, using a disposable private copy. Use a supported SQLite online-backup API/tool to create a consistent snapshot in a private mode-`0700` staging directory outside workspace/build context; protect snapshot as mode `0600`. Mount read-only and seed once into a dedicated persistent volume using the same locked, atomic, success-marked initialization. Never assume this snapshot is an official auth import or invent a credential export/edit. Do not overwrite an existing DB, sidecars, or partial state. If exact compatibility is unknown, stop snapshot import; do not open host data blindly.
- A snapshot is a one-time clone, not live/two-way credential sync. Later host auth changes do not propagate. Never reseed/overwrite container sessions on startup/rebuild. Any approved refresh requires a separate reviewed, supported procedure preserving sessions and credentials; otherwise report refresh unsupported. Repeated starts and rebuilds with the same data volume must leave its identity/data untouched.

If host auth is missing, provider support is uncertain, the daemon cannot access the source, or safe snapshot/import cannot be verified, do not claim no-login readiness. Keep normal container/project development usable when auth is unavailable; do not accidentally break launch with an absent optional bind source. Continue independent environment generation when appropriate, record blocker, and ask only for necessary decision/access. Keep host DB untouched. Never put credentials in repo files, image layers, logs, build args, or broad host mounts.

OpenCode v2 stores provider accounts in SQLite by default under `~/.local/share/opencode/opencode.db`; actual paths may change with XDG, `OPENCODE_DB`, or release channel. Supported legacy auth can be imported during database migration; later SQLite updates are not written back to `auth.json`. Do not treat v1 project config/agents as automatically compatible: inspect the matching v2 schema and migrate project runtime config only as a separately approved, reviewed scope. Do not silently edit shared v1 config or weaken the unrestricted-rights policy for an approved v2 config. If config migration is not approved, report that blocker even if v2 installation is generated.

## Persistence and generated README contract

Document exact start/reopen/rebuild and canonical project build/lint/test commands; all exact pins and evidence; workspace path, services, mounts and ownership; auth mode/source/provider verification or blockers; snapshot host-data disclosure, external cleanup owner, and one-time refresh limits; and how to back up and restore the persistent data volume. Explain that container deletion/rebuild retains the named volume, while deleting that volume loses OpenCode sessions and credentials. Never suggest `docker compose down -v` or any volume deletion as routine cleanup. Session identity depends on keeping the same project workspace path and persisted OpenCode DB; concurrent servers must not open the same DB.

Generated README statements must distinguish observed facts, generated behavior, human decisions, and checks actually run. Include the evidence for dependencies and canonical commands; list blockers and unsupported/untested claims plainly. Do not claim auth reuse, session persistence, or a successful build without acceptance evidence.

## Independent validation

Delegate to `backend-tester`. Use the selected release's matching schema and supported devcontainer CLI/config validation; build and start the destination container with explicit timeouts of at least 10 minutes; verify exact installed OpenCode v2 version; and run evidenced project build, lint, and tests. Inspect supported auth/provider list metadata without login, credential output, or inference. Exercise missing optional auth source without breaking ordinary project launch; verify plain CLI and lifecycle/editor launch gates occur before any DB open when legacy import is required. Verify an unknown/incompatible snapshot release is rejected before host DB access, and test first-use initialization under concurrent launch attempts, repeated starts, pre-existing DB/sidecars, interrupted/partial state, and rebuild using the same volume. Where supported without paid inference, create/list a harmless session using actual documented help/API, record its stable ID, workspace path and provider evidence, rebuild/recreate without deleting volumes, then confirm the same session ID, project path and provider remain. If harmless session creation/listing is impossible without inference or unsupported interfaces, say so and report persistence untested—never fabricate proof. Never delete Docker volumes during validation.

For legacy auth, expose the guarded launcher as the normal `opencode` executable on PATH (including interactive terminals, lifecycle scripts, and editor tasks); keep the underlying binary in a private implementation path. This is startup ordering, not an agent permission restriction. Also verify that an unavailable source leaves project development usable but blocks both plain `opencode` invocation and lifecycle startup before first database open; restoring the source must allow seeding before startup. Cover an already-opened database separately: it must be preserved and reported blocked unless a supported recovery/import has been verified.
