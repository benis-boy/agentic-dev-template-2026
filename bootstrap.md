# Bootstrap From a Product Goal

Use this from the **destination repository root** when a human provides a template GitHub URL and a product goal. This is an onboarding router and review workflow, not permission to overwrite a destination, change global configuration, migrate a runtime, copy credentials, or invent an application. Read the source checkout's `README.md`, this file, and the selected `install.md` or `update.md`. Keep this guidance and `update.md` available in the destination; merge around existing documents rather than replacing them. Check all companion links after relocating files and record source-to-destination path mappings.

## 1. Pin source and protect destination

1. Resolve the provided repository URL to a trustworthy source checkout or snapshot **outside** the destination. Obtain the exact commit ID and inspect whether the source worktree is dirty. Never clone over or inside the destination, import the source `.git`, fetch a newer/moving branch behind the user's request, or silently substitute a revision. If source retrieval/revision cannot be verified, stop and ask.
2. A dirty source requires explicit approval of the exact dirty snapshot and its contents; otherwise use only the recorded commit. Record the source repository identity, commit, cleanliness, and revision permalink generated from that identity and commit (for example, the repository's `/tree/<commit>` URL); do not record an invented/floating reference.
3. Inventory destination root, repository identity and working-tree/index state, existing files and untracked work, app/runtime/config, documentation, tests, container, and any prior setup record. Do not stage, reset, clean, or commit. Keep the human's original product-goal input verbatim in the setup record, distinct from any later approved goals.
4. Classify exactly one current state, with evidence: **new/empty** (no established app/config), **existing app—first adoption** (working product but no credible prior installation), or **existing template—reconciliation** (credible prior template installation). If evidence is mixed, ask and defer the conflicting route. Use `install.md` only for the first two; use `update.md` for reconciliation. Never rerun first-install side effects during update.
5. Ask whether the requested scope is **setup only** or includes **product scaffolding/implementation**. Do not scaffold or modify application behavior unless the human authorizes that scope separately and approves the material plan. Installation of workflow assets is not product implementation.

## 2. Discover intent and propose before editing

Preserve the product goal as stated. Inspect product evidence before proposing changes. Ask about consequential unanswered platform, stack, security, data, scope, or deployment decisions. Offer evidence-based defaults with tradeoffs rather than treating guesses as facts. For new projects, missing canonical build/lint/test commands must be recorded as **not established**, never supplied as fictitious runnable commands. For existing apps, surface where the requested goal conflicts with observed product behavior, established architecture, or constraints; do not replace working architecture merely to resemble this template's seed context.

Before any write, present a scoped merge plan showing destination classification, exact files/paths and behavior to add/change, path/link relocation, placeholder resolution from destination evidence, config and per-agent permission effects, security policy implications, global dependencies/host effects, conflicts/local changes to preserve, runtime compatibility gate, environment choice, and unresolved assumptions. Ask for approval of material choices and permission/security-policy changes. Never edit user/global config or global dependencies without a separate explicit request and approval. If broad template permission behavior conflicts with a meaningful existing policy, preserve the working policy and ask; do not perform blanket cleanup.

The supplied active config and agent files now use native OpenCode V2 shapes. On a V2 destination, inspect the exact runtime/release and review the merge proposal before merging them; preserve unrelated settings and policies. On a V1 destination, stop **the active config/agent merge** until a separately approved runtime upgrade to a compatible V2 release; preserve the working configuration and do not merge native V2 fields. This is not a blanket stop on safe, reviewed onboarding progress: compatible documentation, commands, and skills may be staged individually after checking exact-runtime discovery/parsing, without assuming a copied command is registered. The environment can be reviewed using the source `.opencode/commands/devcontainer.md` and companion guide as plain-text workflow instructions to a currently available capable agent. Keep exact-release runtime compatibility approval separate from container work.

If OpenCode is absent, record runtime and environment as pending; do not require installing a V1 host runtime just to create a V2 container. The human may explicitly approve provisioning the selected runtime/container through the source devcontainer procedure performed by the human or another already available capable coding agent using those source files as plain-text workflow guidance. This is not automatic installation: do not install or upgrade a runtime, login, copy credentials/sessions, migrate config, or change approvals without the relevant separate approval. If no capable agent/operator or approved provisioning path is available, stop honestly and record the exact prerequisite and resume prompt; environment remains pending, not ready.

## 3. Environment decision: devcontainer is the default

Default to reviewing and explicitly invoking the devcontainer workflow after safe asset staging. For a compatible runtime that discovers the command, restart after command/skill changes and explicitly invoke `/devcontainer` in a fresh session. If the runtime is absent or cannot load the command, the human can explicitly approve having the human or another already available capable coding agent follow the source command and guide as plain-text instructions; do not assume command registration or block V2 container work on a host V1 bootstrap. A V1 destination still needs a separately approved runtime upgrade before loading the native V2 config/agents. First inspect existing `.devcontainer`/Compose assets and preserve a valid, working setup; adapt only a reviewed gap. `/devcontainer` must not blindly regenerate existing files. Installation itself only places workflow assets: it never invokes the command, generates container assets, installs/upgrades a runtime, stages credentials, migrates runtime/configuration, or copies sessions.

Skipping requires a concrete reason supplied by the user, an assessment against platform/security/toolchain constraints and reproducible build/test needs, a documented alternative with tradeoffs, and the user's confirmation. A preference such as “I don't want one” without operational specifics is a prompt to ask for specifics, not an agent veto or accepted exception. Assess the stated reason fairly; do not reject a viable alternative arbitrarily. A genuine constraint that cannot support the default may justify a user-confirmed alternative. Until the reason, alternative, or required approval is resolved, environment readiness remains **pending**. Record the reason, constraints, alternative, tradeoffs, and confirmation. Keep separate approval gates for runtime migration, credential/session copying, and destructive replacement.

Do not install Playwright or other global tools on the host before this environment choice. Install dependencies only in the user's selected development environment and only after evidence/approval. If the container is pending, defer environment-dependent checks and report them pending rather than claiming readiness. Apply the exact compatibility and auth gates in the selected workflow; no automatic runtime upgrade or auth operation.

## 4. Durable setup record and resume order

Create `docs/template-setup.md` unless that path already exists. If it exists, treat it as user-owned: inspect, merge and preserve content; if no safe merge location exists, ask before selecting another path. Keep it non-secret. Record at minimum:

- original product-goal input verbatim, separate from approved goal documentation;
- source repository, exact commit, clean/approved-dirty status, and revision permalink;
- destination identity, classification and evidence, prior provenance certainty, and setup-only vs authorized product scope;
- source-to-destination path mappings for commands, skills, docs and references; checked links and unresolved links;
- decisions and approvals, rejected/deferred alternatives, conflicts, unknowns and explicit “not established” commands;
- ordered phases and independent status for workflow assets, runtime/config compatibility, environment, goals, checks, and authorized product outcome;
- devcontainer retained/adapted/generated status, or user-confirmed exception reason, assessed constraint, alternative, tradeoffs and confirmation;
- runtime/model/version evidence, environment evidence, commands/results with context, and unresolved blockers;
- exact next action/resume prompt that names this record and the first incomplete phase. Do not put tokens, credentials, session data, or private auth paths in the record.

Update the record as work progresses; never reset it on restart or template update. Preserve initialized project goal tree/proof/index on updates; do not rerun `/init-goals` by default. For first setup, use this order and stop at approvals/blockers:

1. Acquire and pin source; classify; inspect destination; record the original product-goal input and initial evidence. Do not treat the template source as the destination product or initialize goals for the source repository.
2. Review and approve the scoped merge proposal, including product-work scope and material permissions/configuration.
3. Install or reconcile distributable workflow assets only. Check every relocated companion reference against the destination path map. Never copy this template's `README.md`, source `.devcontainer`, or maintainer-only assets as product assets: exclude the source-only `.opencode/rules/template-maintainers.md`, its `.opencode/opencode.json` `instructions` entry, and `.opencode/docs/template-onboarding.md`. Preserve unrelated destination instructions and rules. Do not copy the goal skill's seed tree/proof/index as authoritative goals.
4. Restart the runtime after compatible config/agent/skill/command changes; use a **fresh session** and resume from `docs/template-setup.md`. Do not load native V2 config/agents into a V1 runtime. If the runtime is absent or the command is not known to be registered, record the pending prerequisite and offer the approved plain-text procedure described above.
5. Explicitly follow the devcontainer workflow by default: invoke `/devcontainer` only when the active compatible runtime is known to discover it, otherwise use the approved human/operator or existing-capable-agent plain-text procedure. No host V1 bootstrap is required solely for V2 container work. Retain/adapt existing valid setup. If runtime changes, restart and use another fresh session before relying on it. Keep runtime upgrades, auth/session copy, and destructive changes separately approved. If required provisioning cannot proceed, stop with an exact resume prompt and environment readiness pending; do not claim ready.
6. For first goal initialization only, invoke `/init-goals` with the setup record as context after confirming a compatible runtime and registration of both the command and its `design` agent. Otherwise preserve the uninitialized seeds, keep goals pending, and record the next action: complete any separately approved runtime/agent compatibility work, confirm registration, restart into a fresh session, then invoke `/init-goals` with the setup record. Its discovery and write phases remain separately approval-gated; preserve its requirement for human correction/approval before authoritative goal writes. For reconciliation, preserve existing goals and do not reinitialize.
7. If and only if product implementation is separately authorized, implement the first approved vertical slice and collect the proof appropriate to that outcome. Otherwise stop at workflow setup and list product work as not started.

## 5. Report evidence, not completion by implication

Report these statuses independently; installation is not product readiness:

| Dimension | Allowed report |
|---|---|
| Workflow assets | not started / partial / installed and links checked |
| Runtime/config | pending / compatible evidence recorded / blocked; distinguish v1/v2 and approval |
| Environment | pending / ready with checks / user-confirmed documented alternative / blocked |
| Goals | not initialized / proposal awaiting approval / approved and written / preserved on update |
| Checks | not runnable / commands not established / runnable / exact results recorded |
| First product outcome | out of scope / not started / in progress / proven by named evidence |

Identify remaining approvals, blockers, risks and exact next action. A documented end-to-end plan or one-shot static review is not an implemented runner and does not prove model availability, browser operation, real agent-led installation, runtime compatibility, container build, authentication, or product behavior. Preserve destination project testing and proof discipline. Report any unverified onboarding transitions plainly rather than treating written instructions as executed evidence.
