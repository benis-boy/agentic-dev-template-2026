# Reconcile an Existing Template Installation

Use this procedure **from the destination repository root** when updating an existing installation of this template. The goal is a reviewed reconciliation to the current template, not a fresh install, reset, or blind copy. The destination may have drifted substantially, contain better local ideas, or already use OpenCode v2. Do not run `install.md` as this update procedure: it includes first-install dependencies and fresh-session goal-initialization follow-ups that must not be repeated blindly.

## 1. Establish source and destination evidence

1. Confirm the current directory is the destination repository root. Record its working-tree and index state without staging, resetting, cleaning, or committing anything. Preserve staged and unstaged user work exactly; do not include unrelated changes in edits or validation.
2. Identify the template source actually available to this session: its repository/worktree or an explicitly supplied source snapshot. Record its path, branch, exact commit/revision, and whether it has uncommitted changes. Do not assume the current directory is the template, fetch/update a branch, or substitute a moving remote version. If no trustworthy source is accessible, ask for it and stop rather than guessing the desired state.
3. Record the target's existing installation revision/source when known (for example, a prior install record, branch/commit, or matching template content). Use a common ancestor/prior baseline for three-way classification when credible. If provenance is unknown, compare current source and target as a two-way comparison and label authorship/provenance uncertain; do not claim a target change is new, local, or upstream solely from its wording.
4. Determine the target's OpenCode runtime version/channel and inspect its matching config/schema/help without exposing secrets. Inventory project and inherited configuration, agent/skill/command/doc layouts, references, product context, and existing user changes before editing. Read the current source `README.md`, `install.md`, `AGENTS.md`, `.opencode/opencode.json`, all seven `.opencode/agents/*.md`, every recursively nested `.opencode/skills/**` asset, all `.opencode/commands/**`, and relevant `.opencode/docs/**`. Treat those source files as current behavioral authority; use README/install as discovery maps, not as an instruction to re-run installation side effects. Compare the complete dynamically discovered source inventory with target content, including future source additions. Do not read large JSON files wholesale; inspect only relevant schema/fields using supported tools.

## 2. Build a behavior-based reconciliation map

Compare behavior and contracts, not just file text. Map source and destination paths, including adapted/renamed locations and links between companion assets. Check that destination command/skill/doc references resolve after merging.

For each meaningful difference, classify it as one of:

- **Template update:** current source behavior is desired and compatible.
- **Project adaptation:** target-specific facts, paths, commands, policies, or architecture that must remain accurate.
- **Possible upstream improvement:** local behavior appears to improve the reusable template; preserve it and report it to the human with evidence.
- **Unresolved conflict:** intent, provenance, compatibility, or correct behavior is unclear; ask the human before changing it.

The current template is the technical lead for common architecture, roles, and reusable workflows, but it does not prove every target detail is worse. Preserve accurate project facts, goals/proof evidence, custom agents, skills, tools, providers, plugins, commands, security settings, and demonstrated improvements. Do not replace whole files, auto-delete target-only files, let a same-name source file silently win, or call a difference “better” without behavioral evidence. Merge compatible scoped changes and batch human questions about material conflicts. For a candidate upstream improvement, notify the human before concluding: give source and target paths, concise before/after behavior, rationale, concrete evidence, compatibility implications, and the choice needed. Never edit the template source or downgrade the target automatically; any upstream contribution is a separate human-approved task.

Permission language describes intended role scope, not enforced technical rights. The current template explicitly sets root and every supplied agent permission to `allow`; reconcile that current policy accurately, but do not silently change the target's unrelated/global security policy or erase a meaningful local restriction. Surface a conflict and get approval for any change whose effect is material. Do not claim role instructions or OpenCode rules establish OS-level or prompt-injection security.

## 3. Reconcile the current workflow and runtime without reinitializing

Use the checked-out source content, not a memorized file list, as the current inventory. In particular, account for these current template behaviors and check the whole supplied tree for changes/additions:

- Seven distinct roles: Design is sole primary coordinator and never runs tests; Worker owns bounded implementation and focused test authoring but returns tests unexecuted; once validation is assigned, the appropriate tester exclusively owns execution and test corrections; Scout and Reviewer are read-only; Heavy is a sole-owner emergency replacement for one explicit mode, never a duplicate or self-certifier. These are role instructions, not technical access restrictions.
- Recursively distributed skill assets, their intended applicability, commands and companion documentation. Preserve destination-specific skills and all links; do not stop at the two currently known skill names or impose skill allowlists as rights controls. The goal-oriented skill and `/init-goals` are reusable templates only: do not initialize, reinitialize, infer, or rewrite goal files or product documentation during this reconciliation. If a destination already initialized goals, retain its tree, proof inventory, index, and evidence; preserve full plain-text outcomes and never treat goal IDs as authoritative substitutes for those outcomes. Update only a specifically compatible reference if approved.
- The optional `/devcontainer` command and companion guide are copied workflow assets: reconcile both to the current source while preserving compatible local improvements. Updating these assets does not authorize invoking the command, generating a container, or changing an existing container; those actions require an explicitly requested container task.
- `AGENTS.md` is durable destination context: preserve accurate project facts, boundaries, invariants, workflows, and living product-summary requirements. Do not carry source placeholder facts over as target facts.
- The current template source's runtime/model policy and its version-specific config shape. The known v1 template pins Design and emergency Heavy to `github-copilot/gpt-6.1-sol`, normal subagents to `github-copilot/gpt-6-luna`, disables supplied built-in agents, and does not define `subagent_depth`. Verify these against the exact source revision before acting. Never infer a different model, substitute an unavailable model, or silently change runtime, dependencies, auth, plugins, or inference behavior. If a pinned model cannot be confirmed, preserve the working target configuration and report that portion blocked.
- A v2 target is in scope for reconciliation: do **not** stop the whole update at install.md's first-install v1 gate. Use the target's exact v2 release/schema and current v2 documentation, then compare behavior with v2-compatible fields. Do not paste v1 frontmatter/config into v2 or treat a separate v2 migration plan as an automatic migration approval. If translating a desired behavior requires a shared runtime migration, obtain approval, identify host/project impacts, and use a verified v2-supported representation; otherwise preserve the working runtime and report the unresolved part.
- Current source excludes `.opencode/docs/e2e-runner-feature.md` from automatic installation and requires a human follow-up for a project-specific runner. Do not copy or adapt that plan automatically as part of update. Notify the human if relevant and preserve any existing destination runner/plan.

The installer is not an update script. Do not repeat its global Playwright CLI/browser installs, model inference, fresh goal initialization, or broad permission cleanup. Check existing Playwright skill and executable/browser state only as needed; never install globally without a separate explicit request. Do not erase local runtime config just to resemble the source seed.

## 4. Apply only reviewed, bounded merges

Make the smallest compatible changes in the destination's established layout. Preserve unrelated material and target-specific adaptations. Resolve placeholders from target evidence only when editing an applicable template section; never replace existing product facts with generic seed text. For uncertain or material conflicts, leave the affected content unchanged until the human decides. Do not remove obsolete files automatically: removal requires reviewed provenance and explicit approval, with references checked first. If the source tree has uncommitted changes, distinguish those from the reviewed template revision and do not treat them as authoritative without confirmation.

## 5. Validate and report honestly

Use the destination's exact runtime/schema and narrowly relevant existing checks. Confirm merged references resolve, changed content has no unintended placeholder, the target config retains its version-specific model/agent semantics, and the meaningful diff contains only intended changes. Assign execution to the destination's canonical tester when available; Design does not run tests. Do not invent tests or run arbitrary application inference, login, package installation, or auth migration to validate a documentation/config reconciliation. Preserve all unrelated staged/index state; do not stage, reset, commit, or clean.

Report the source revision and cleanliness, target runtime/version, baseline/provenance certainty, paths reconciled and behavior merged, local behavior retained, any source improvements proposed with evidence, unresolved decisions, exact validation/outcomes, placeholders or reference gaps, model/runtime blockers, and required human follow-ups. State whether a runtime restart is needed. A reconciliation is **partial**, not complete, if an essential role/config/runtime conflict or unavailable authoritative source remains unresolved; clearly name what needs human approval. Do not imply that goals were initialized or that `/devcontainer` ran.
