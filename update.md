# Reconcile an Existing Template Installation

Use this procedure **from the destination repository root** when updating an existing installation of this template. Read the installed `bootstrap.md` and resume from its non-secret `docs/template-setup.md` record; preserve and update that record rather than resetting it. Reassess documented council and environment decisions and report unresolved readiness. Updating does not invoke `/init-council` or `/devcontainer`, generate a missing setup, run container operations, migrate a runtime, copy credentials/sessions, or force repeated setup work. It may include a reviewed, bounded file-only repair of an existing setup when current contract evidence supports compatibility. The goal is reviewed reconciliation, not a fresh install, reset, or blind copy. The destination may have drifted substantially, contain better local ideas, or already use OpenCode v2. Do not run `install.md` as this update procedure: first-install side effects and goal-initialization follow-ups must not be repeated blindly.

## 1. Establish source and destination evidence

1. Confirm the current directory is the destination repository root. Record its working-tree and index state without staging, resetting, cleaning, or committing anything. Preserve staged and unstaged user work exactly; do not include unrelated changes in edits or validation.
   Read the setup record if present. Retain original goal input, source provenance, destination classification, approved decisions, prior results, and environment exception evidence; append/update only the phase affected by this reconciliation. If absent, create it only as part of a reviewed merge and preserve existing documentation.
2. Identify the template source actually available to this session: its repository/worktree or an explicitly supplied source snapshot. Record its path, branch, exact commit/revision, and whether it has uncommitted changes. Do not assume the current directory is the template, fetch/update a branch, or substitute a moving remote version. If no trustworthy source is accessible, ask for it and stop rather than guessing the desired state.
3. Record the target's existing installation revision/source when known (for example, a prior install record, branch/commit, or matching template content). Use a common ancestor/prior baseline for three-way classification when credible. If provenance is unknown, compare current source and target as a two-way comparison and label authorship/provenance uncertain; do not claim a target change is new, local, or upstream solely from its wording.
4. Determine the target's OpenCode runtime version/channel and inspect its matching config/schema/help without exposing secrets. Inventory project and inherited configuration, agent/skill/command/doc layouts, references, product context, and existing user changes before editing. Read the current source `README.md`, `install.md`, `AGENTS.md`, `.opencode/opencode.json`, and every dynamically discovered `.opencode/agents/*.md` definition, every recursively nested `.opencode/skills/**` asset, all `.opencode/commands/**`, and relevant `.opencode/docs/**`. Treat those source files as current behavioral authority; use README/install as discovery maps, not as an instruction to re-run installation side effects. Compare the complete dynamically discovered **distributable** source inventory with target content, including future source additions. Explicitly exclude the source-only `.opencode/rules/template-maintainers.md`, its `.opencode/opencode.json` `instructions` entry, and `.opencode/docs/template-onboarding.md`; do not blanket-exclude `.opencode`. Preserve unrelated target instruction entries and rules and never delete a target-only rule merely because it is absent from source. Do not read large JSON files wholesale; inspect only relevant schema/fields using supported tools.

## 2. Build a behavior-based reconciliation map

Compare behavior and contracts, not just file text. Map source and destination paths, including adapted/renamed locations and links between companion assets. Check that destination command/skill/doc references resolve after merging.

For each meaningful difference, classify it as one of:

- **Template update:** current source behavior is desired and compatible.
- **Project adaptation:** target-specific facts, paths, commands, policies, or architecture that must remain accurate.
- **Possible upstream improvement:** local behavior appears to improve the reusable template; preserve it and report it to the human with evidence.
- **Unresolved conflict:** intent, provenance, compatibility, or correct behavior is unclear; ask the human before changing it.

Keep reusable workflow asset availability separate from destination feature state. A current `/init-council` or `/devcontainer` command, guide, skill, or other reusable definition proves only that the corresponding authoring/workflow asset is available; it does not prove generated council definitions/notes or a usable project environment exist. Use the setup record, mapped/adapted paths, actual destination files, and current source/project contract evidence to classify each feature independently as **absent**, **incomplete**, **needs-compatible-refresh**, **adapted-current**, or **blocked**. This is a behavior/readiness assessment, not a version ledger: age, text equality, a title, or roster size is not evidence of staleness. If runtime recognition, build/readiness, provenance, or another necessary fact is unverified, report **unknown** and the evidence gap rather than labeling the feature outdated. A confirmed documented alternative to a devcontainer is not a missing-container defect. Include the evidence, proposed action, owner, retained adaptations, follow-up, and verification gaps in the reviewed plan and existing setup record.

For the council, inspect generated definitions and current shared/member notes at mapped locations, then assess whether actual project needs remain covered; do not infer a council from authored initializer assets. For the environment, inspect root `.devcontainer`/Compose/lifecycle assets and any documented viable alternative; do not infer readiness from the reusable guide or source repository's own container. Inspect adapted or renamed locations rather than requiring canonical filenames.

The current template is the technical lead for common architecture, roles, and reusable workflows, but it does not prove every target detail is worse. Preserve accurate project facts, goals/proof evidence, custom agents, skills, tools, providers, plugins, commands, instruction entries, rules, security settings, and demonstrated improvements. Do not replace whole files, auto-delete target-only files, let a same-name source file silently win, or call a difference “better” without behavioral evidence. Merge compatible scoped changes and batch human questions about material conflicts. For a candidate upstream improvement, notify the human before concluding: give source and target paths, concise before/after behavior, rationale, concrete evidence, compatibility implications, and the choice needed. Never edit the template source or downgrade the target automatically; any upstream contribution is a separate human-approved task.

Role language describes intended scope, not enforced technical rights. The current template root and supplied agents use native V2 ordered catchall allow rules, including access to external paths, with one explicit skill-tool restriction: only `design` and `heavy-subagent` may load `goal-oriented-design`. The root denies that skill after its catchall; Design and Heavy allow it after theirs, and every other supplied agent denies it after theirs. Agent rules follow root rules, so inspect additional destination agents for broad allows that would override the root deny and surface conflicts. Role instructions otherwise remain prompts, not technical restrictions. Reconcile that behavior accurately, but do not silently change the target's unrelated/global security policy or erase meaningful local asks/denials. Surface a conflict and obtain approval for any material permission change. Do not claim role instructions or OpenCode rules establish OS-level or prompt-injection security.

## 3. Reconcile the current workflow and runtime without reinitializing

Use the checked-out source content, not a memorized file list, as the current inventory. In particular, account for these current template behaviors and dynamically check the whole distributable tree for changes/additions, applying only the explicit exclusions in step 11:

- Distinct roles: Design is sole primary coordinator and never runs tests; agent-maintainer owns agent-definition Markdown and specifically assigned `AGENTS.md` instruction maintenance; Worker owns bounded implementation, focused test authoring, and scoped backend/service/script/config/static/backend-E2E execution and fixes; frontend-tester exclusively owns UI/browser/accessibility/frontend-static/E2E execution and its exact allowlisted locator-attribute edits. Scout and Reviewer are read-only; Heavy is a sole-owner emergency replacement for one explicit mode, never a duplicate or self-certifier. These are role instructions, not technical access restrictions. A worker assigned backend verification-only does not repair product or environment behavior; a fresh non-author worker can provide independent execution when required. Author self-review is not independent validation. Preserve any separate independent-acceptance requirement without restoring a default backend-tester chain.
- Recursively distributed skill assets, their intended applicability, commands and companion documentation. Discover and preserve all destination-specific skills, links, and shared `AGENTS.md` discovery cues. Preserve the specific `goal-oriented-design` loading restriction to Design and Heavy; other specialists receive relevant outcomes and proof requirements inline. Do not impose other skill allowlists as rights controls. The goal-oriented skill and `/init-goals` are reusable templates only: do not initialize, reinitialize, infer, or rewrite goal files or product documentation during this reconciliation. If a destination already initialized goals, retain its tree, proof inventory, index, and evidence; preserve full plain-text outcomes and never treat goal IDs as authoritative substitutes for those outcomes. Update only a specifically compatible reference if approved.
- `/devcontainer` remains the default explicit onboarding environment action, separate from updating its reusable command and guide. If no actual setup exists, explicitly tell the human to invoke `/devcontainer` only after compatible staging and confirmation that the command/agent is available; honor its default exception process. Do not initialize it during template update. A partial setup is reconciled by the same command, not by blindly restarting or replacing files. For an existing setup, a reviewed plan may include a bounded, compatible **file-only** merge/repair of configuration or scripts when current evidence shows the change preserves project container choices, services, tool constraints, stable workspace/volume identities, data, selected auth mode, and valid local improvements. No build/start/rebuild/stop, provisioning, runtime migration, silent pin bump, credential/session copy, database reseed, lock weakening, or activation is authorized. Protected, uncertain, or out-of-scope work requires the command's continuation and its existing separate approvals; until performed and checked, report refresh incomplete. A confirmed alternative is recorded as such, not treated as a defect. Preference-only skip requires clarification; unresolved decisions remain pending.
- `/init-council` is also an explicit follow-up, not an effect of installing its reusable command/guide. If the actual council is absent, tell the human to invoke `/init-council <subject or ambition>` after compatible staging and confirmation that its command and required agent are available. Do not initialize a council during update. A partial council uses that same command to reconcile its selected scope; do not overwrite outputs blindly. If the user explicitly defers an optional council, record the deferral without blocking unrelated environment or product work. For an existing council, check whether its mandates still cover actual project scope, architecture, consequential questions, risks, dependencies, and integrations; propose justified compatible additions/updates without automatic pruning or renaming. At least one substantive expert must have source-code familiarity on an existing codebase (see the council companion); documentation or an architect title alone is not evidence. Keep note refresh within the active manager's assigned documentation-only scope; otherwise report the exact outstanding note work and `/init-council` refresh continuation rather than inventing a publisher or launching a manager.
- `AGENTS.md` is durable destination context: preserve accurate project facts, boundaries, invariants, workflows, and living product-summary requirements. Do not carry source placeholder facts over as target facts.
- The current template source's runtime requirements, model pins, and native V2 config shape. Design, agent-maintainer, and emergency Heavy are pinned to `github-copilot/gpt-6.1-sol`; normal subagents use `github-copilot/gpt-6-luna`. Four built-in agents are disabled, and `subagent_depth` is not defined. Verify these against the exact source revision before acting. Never infer a different model, substitute an unavailable model, or silently change runtime, dependencies, auth, plugins, or inference behavior. If a pinned model cannot be confirmed, preserve the working target configuration and report that portion blocked.
- A V2 target is in scope for reconciliation: do **not** stop the whole update at install.md's first-install compatibility gate. Use the target's exact V2 release documentation and inspect the native V2 shapes, then compare behavior. Do not paste V1 fields into V2 or treat this guide as approval to upgrade a V1 runtime. A V1 destination must keep its active config/agents unchanged until a separately approved runtime upgrade to a compatible V2 release. If a shared runtime migration is required, obtain approval and identify host/project impacts; otherwise preserve the working runtime and report the unresolved part.
- Current source excludes `.opencode/docs/e2e-runner-feature.md` from automatic installation and requires a human follow-up for a project-specific runner. Do not copy or adapt that plan automatically as part of update. Notify the human if relevant and preserve any existing destination runner/plan.

The installer is not an update script. Do not repeat global Playwright CLI/browser installs, model inference, fresh goal initialization, or broad permission cleanup. Check existing Playwright skill and executable/browser state only as needed; never install globally without a separate explicit request. Preserve meaningful existing security policy; the root/per-agent V2 catchall allow is intended template behavior, not approval to remove material target restrictions. Obtain explicit approval for material permission changes and never edit global config without a separate request. Do not erase local runtime config just to resemble the source seed.

## 4. Apply only reviewed, bounded merges

### Reconcile the retired backend-tester role

For an existing destination, reconcile the source role retirement as a narrowly scoped behavior migration, not a deletion inferred from source absence:

1. Positively establish whether a destination backend-tester definition is derived from the retired template role. Compare its content/provenance with the source and credible baseline, including mapped or renamed equivalents where the destination's conventions support that mapping. Inspect the current worker and its routing/reference definitions too. A same-name agent may be custom or repurposed; a missing source file, a matching name alone, or unknown provenance is not deletion authority. Preserve unrelated/custom agents and ask about material uncertainty.
2. Inventory destination-specific backend test, lint, build, and static-check commands; prerequisites; cleanup and approval limits; known coverage references; environment-stop rules; and reliability constraints recorded in the old agent or related destination guidance. Transfer still-applicable adaptations into the destination worker or authoritative project instructions, merging with current worker behavior rather than wholesale-copying the old definition. Preserve goal trees, proof inventories, status/evidence, and prior results; do not reinitialize them. Change executor/routing metadata only when genuinely necessary and narrowly approved, without replacing evidence.
3. Put the confirmed retired role name, mapped path/ID, adaptations to transfer, reference/config changes, approval needs, and verification gaps in the reviewed scoped update plan. The source retirement is approved; deletion from a destination still needs explicit approval that covers the positively identified obsolete definition unless that exact deletion is already within the reviewed scope. Do not relax this rule for other source-missing assets.
4. Inventory in-scope destination references and registrations, including agent instructions, commands/skills/docs, aliases, and project-local JSON agent entries, permissions, or explicit catalogs when present and template-related. Route agent-Markdown edits through agent-maintainer; route JSON integration to its owner/Design. Update only confirmed template-related routes to Worker with the correct backend scope. Establish replacement behavior and routes before removing a confirmed obsolete definition/config entry. Do not edit blanket global/inherited controls; surface conflicts or uncontrolled inherited duplicate registrations. Do not weaken user policy or repurpose an unrelated same-name agent.
5. If required transfer, route, permission, runtime compatibility, provenance, or approval cannot be established, leave the needed executor intact and report the affected migration partial/blocked; do not claim completion after a half-removal. If already migrated or no retired role is present, verify the intended routing and make no forced duplicate move or unnecessary deletion. Preserve the source-trust/dirty-revision and three-way classification, stage/index/user work, the V1 active-file gate, runtime/auth/provisioning no-side-effect rules, source-only exclusions, and the ban on goal initialization/rebaselining. After compatible role/config changes, request a runtime restart and fresh session; file removal alone does not prove runtime availability.

Completion requires evidence that destination-specific checks and constraints remain represented, Worker execution is scoped to the backend domain, no in-scope route/registration still points to the retired template ID, and frontend-tester and independent Reviewer boundaries remain distinct. Record exact final-state checks and outcomes, whether execution was author or independent, and all unrun/unknown gaps in the existing setup record. Do not create a new ledger. Unknown inherited/runtime registrations are gaps, not assumed passes.

Make the smallest compatible changes in the destination's established layout. Preserve unrelated material and target-specific adaptations. Resolve placeholders from target evidence only when editing an applicable template section; never replace existing product facts with generic seed text. For uncertain or material conflicts, leave the affected content unchanged until the human decides. A reviewed update plan may perform bounded non-destructive **file-only** repairs to existing devcontainer configuration/scripts and council generated definitions through their proper owners; retain local improvements and all protected data/identity/auth choices. This narrow allowance does not generate missing features, invoke setup commands (`/init-council` or `/devcontainer`), activate roots, or perform container/runtime operations. It does not prohibit approved read-only inspection or static verification commands. Leave protected, uncertain, or out-of-scope changes for the relevant command/implementation continuation and approvals, and mark the affected feature incomplete until that work is performed and checked. Definitions and operational agent instructions belong to `agent-maintainer`; executable container work belongs to a worker; JSON/runtime integration belongs to its implementation owner/Design, not the maintainer. Do not remove obsolete files automatically: removal requires reviewed provenance and explicit approval, with references checked first. If the source tree has uncommitted changes, distinguish those from the reviewed template revision and do not treat them as authoritative without confirmation.

## 5. Validate and report honestly

Use the destination's exact runtime/schema and narrowly relevant existing checks. Confirm merged references resolve, changed content has no unintended placeholder, the target config retains its version-specific model/agent semantics, and the meaningful diff contains only intended changes. Worker owns backend/service/script/config/static/backend-E2E execution and scoped test fixes; frontend-tester retains UI/browser/accessibility/frontend-static/E2E execution and its exact locator-edit boundary. Preserve any independent-acceptance requirement, using a fresh non-author verification-only worker when appropriate; author self-review is not independent. Design does not run tests. Do not invent tests or run arbitrary application inference, login, package installation, or auth migration to validate a documentation/config reconciliation. Preserve all unrelated staged/index state; do not stage, reset, commit, or clean.

Report workflow-asset merge success separately from feature completeness, review/validation, activation, and unknowns. Include the source revision and cleanliness, target runtime/version, baseline/provenance certainty, mapped paths reconciled and behavior merged, local behavior retained, council coverage assessment, unresolved decisions, exact checks/outcomes, placeholders or reference gaps, and model/runtime blockers. Update the existing setup record without creating a tracking service, and report workflow assets, council, environment, goals, checks, and first product outcome independently. For every absent or incomplete feature, give the exact conditional follow-up and a concrete subject/context derived from destination evidence (for example, `/init-council <project's evidenced domain/ambition>` or `/devcontainer`); use a safe placeholder and state what intent is unknown when indispensable. Confirm command/agent availability before asking the human to invoke it. State whether a runtime restart is needed and the exact resume prompt. A reconciliation is **partial**, not complete, while an essential in-scope refresh, review, validation, activation, compatibility decision, or readiness gate remains incomplete or unknown. An explicitly deferred optional council is recorded as deferred, not as a blocker to unrelated environment or product work; its feature status is still not complete. Do not imply that goals were initialized, a feature was generated, runtime recognized a council, or `/devcontainer` ran.
